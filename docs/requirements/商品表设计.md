## 1. 当前范围与技术选择

- 项目采用前后端分离与微服务架构；现有前端为 Vue 3 项目。
- 后端初始化采用 Java 21、Maven、Spring Boot 4.0.8。
- 当前初始化选择 Lombok、Spring Web、MySQL Driver；MyBatis、参数校验、JWT 鉴权及其他微服务依赖在实现相应功能时通过 Maven 添加，并核对版本兼容关系。
- 本文确定商品主表，不创建品牌表，品牌名称直接保存在商品表中。新增详情路径表按需求 005 单独设计，由商品服务与同一商品数据源管理。
- 本文 SQL 适用于讨论中参考的 MySQL 8.0.27；实际数据库环境尚未验证。

## 2. 商品主表的设计约定

数据库实际名称保留为 `nesmartmall_product`，作为商城共用数据库，不执行改名或迁库。商品表名称仍为 `product`，后续账户表 `account` 也创建在该库中；商品表由商品服务管理，账户表由认证服务管理。

一行表示一个商品，而不是一个商品规格或套餐对应的 SKU。首页销量前八与全部商品分页均按商品粒度返回，每个商品在同一页只出现一次。新增分页接口不需要修改商品表结构，接口及 PageHelper 要求见 [需求.md 第 9 节](./需求.md#9-需求-003查看全部商品与-pagehelper-分页查询)。

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `id` | BIGINT | 自增主键；接口返回 ID 时建议转为字符串 |
| `name` | VARCHAR(200) | 必填，不能是空字符串或全空格 |
| `model` | VARCHAR(100) | 商品型号，允许为空 |
| `brand_name` | VARCHAR(100) | 品牌名称，允许为空；不单独建品牌表 |
| `category_id` | BIGINT | 分类 ID，未分类时允许为空 |
| `cover_image_url` | VARCHAR(1024) | 商品封面图片地址，允许为空；图片文件不存入该字段 |
| `price` | BIGINT | 展示价格，以整数分存储；未确定时允许为空 |
| `sales_count` | BIGINT | 非负销量汇总值；新商品默认 0，统计口径待确认 |
| `status` | TINYINT | 0：草稿；1：上架；2：下架；默认草稿 |
| `is_deleted` | TINYINT | 0：正常；1：已删除；默认正常 |
| `created_at` | DATETIME(3) | 创建时间，精度为毫秒 |
| `updated_at` | DATETIME(3) | 最后修改时间，精度为毫秒 |

商品上下架状态与删除标记分别保存。首页查询采用 `status = 1 AND is_deleted = 0`。

“全部”是跨分类查询条件，不作为一条商品分类记录保存。分类表建立后再补充分类关联约束；商品参数后续由关联表保存。多规格商品的库存、规格和销售价格由后续 SKU 设计落实。

## 3. 最终建库与建表 SQL

以下 SQL 为新建数据库和商品表的定义，尚未执行。若数据库中已存在 `product` 表，应先核对结构并编写迁移语句；下面的 `CREATE TABLE` 不会修改已有表。

```sql
CREATE DATABASE IF NOT EXISTS nesmartmall_product
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

USE nesmartmall_product;

CREATE TABLE product (
    id              BIGINT NOT NULL AUTO_INCREMENT COMMENT '商品ID',
    name            VARCHAR(200) NOT NULL COMMENT '商品名称',
    model           VARCHAR(100) NULL COMMENT '商品型号',
    brand_name      VARCHAR(100) NULL COMMENT '品牌名称',
    category_id     BIGINT NULL COMMENT '分类ID，未分类时为空',
    cover_image_url VARCHAR(1024) NULL COMMENT '商品封面图片地址',

    price           BIGINT NULL
                    COMMENT '展示价格，单位分；未确定时为空',

    sales_count     BIGINT NOT NULL DEFAULT 0
                    COMMENT '按约定口径汇总的商品销量',

    status          TINYINT NOT NULL DEFAULT 0
                    COMMENT '商品状态：0草稿，1上架，2下架',

    is_deleted      TINYINT NOT NULL DEFAULT 0
                    COMMENT '删除标记：0正常，1已删除',

    created_at      DATETIME(3) NOT NULL
                    DEFAULT CURRENT_TIMESTAMP(3)
                    COMMENT '创建时间',

    updated_at      DATETIME(3) NOT NULL
                    DEFAULT CURRENT_TIMESTAMP(3)
                    ON UPDATE CURRENT_TIMESTAMP(3)
                    COMMENT '最后修改时间',

    PRIMARY KEY (id),

    KEY idx_product_sales (
        status, is_deleted, sales_count DESC, id ASC
    ),

    KEY idx_product_category (category_id),

    CONSTRAINT chk_product_name
        CHECK (CHAR_LENGTH(TRIM(name)) > 0),

    CONSTRAINT chk_product_price
        CHECK (price IS NULL OR price >= 0),

    CONSTRAINT chk_product_sales
        CHECK (sales_count >= 0),

    CONSTRAINT chk_product_status
        CHECK (status IN (0, 1, 2)),

    CONSTRAINT chk_product_deleted
        CHECK (is_deleted IN (0, 1))
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '商品主表';
```

## 4. 金额存储与接口转换

最终采用整数分方案，替代先前讨论中的 `price_yuan DECIMAL(12,2)` 数据库字段。首页与分页接口沿用现有 `price` 字段，以整数分返回；前端除以 100 后展示为元，不使用此前草案中的 `priceYuan` 响应字段。

| 实际金额 | 数据库 `price`（分） | 接口 `price`（分） |
| --- | --- | --- |
| 12 元 | 1200 | 1200 |
| 12.34 元 | 1234 | 1234 |
| 零元 | 0 | 0 |
| 价格未确定 | NULL | null |

数据库价格可以用 Java `Long` 接收；现有 `ProductCardVO.price` 使用 `BigDecimal`，响应数值仍须是整数分，不能在后端转为元后再交给现有前端除以 100。

前端展示金额时可以格式化为两位小数；`null` 展示“价格待确认”。价格未确定不能用 0 代替。

## 5. 主键、索引与约束说明

### 5.1 主键与索引

- `PRIMARY KEY (id)`：商品 ID 唯一且不能为空，并建立主键索引。`AUTO_INCREMENT` 是字段设置，负责生成递增 ID。
- `idx_product_sales`：联合索引，前两个字段匹配上架与删除状态，后两个字段匹配销量降序、同销量 ID 升序的排名规则。
- `idx_product_category`：帮助按分类 ID 查询商品。后续如果确定分类销量榜需求，再评估替换为分类排名联合索引。
- 索引不会自动保证查询结果的顺序，查询仍须显式写 `ORDER BY`；索引也会占用空间，并增加相关字段的写入维护成本。

### 5.2 数据校验约束

`CONSTRAINT` 后面是约束名称，`CHECK` 后面是校验条件。插入或修改数据违反条件时，数据库拒绝操作。

| 约束 | 校验内容 |
| --- | --- |
| `chk_product_name` | `TRIM` 去掉名称两端的普通空格后，`CHAR_LENGTH` 检查至少还有一个字符；应用层仍需进行名称校验 |
| `chk_product_price` | 允许价格为空，否则价格必须非负 |
| `chk_product_sales` | 销量必须非负 |
| `chk_product_status` | 商品状态只能为 0、1、2 |
| `chk_product_deleted` | 删除标记只能为 0、1 |

MySQL 从 8.0.16 起正式执行 `CHECK` 约束，因此参考版本 8.0.27 支持这些校验。

### 5.3 存储与字符设置

- `ENGINE = InnoDB`：使用支持事务和行级锁的 InnoDB 引擎。
- `DEFAULT CHARSET = utf8mb4`：支持中文、英文及表情符号等字符，避免沿用参考表的 `utf8mb3`。
- `COLLATE = utf8mb4_0900_ai_ci`：基于 Unicode 9.0 的比较和排序规则；`ai` 表示忽略重音差异，`ci` 表示忽略大小写。比较规则不会改写存储的原始文字。
- `DATETIME(3)` 的时间字段会使用会话当前时间生成值，后续需统一数据库连接和应用的时间约定。

## 6. 首页销量前八查询与性能方案

```sql
SELECT id, name, model, brand_name, category_id,
       cover_image_url, price, sales_count
FROM product
WHERE status = 1
  AND is_deleted = 0
ORDER BY sales_count DESC, id ASC
LIMIT 8;
```

查询跨全部分类，按销量降序返回最多八个商品；销量相同时按 ID 升序排列。不足八个时返回实际数量，无商品时返回空列表。接口 `price` 保持数据库的分单位，由前端转换为元展示。

分类名称和商品参数后续批量获取，避免一对多关联使 `LIMIT 8` 限制的是关联行数而不是商品数量。

百万行数据不代表每次执行 `ORDER BY` 都会排序百万行。匹配的索引可以提供顺序，数据库找到足够结果后可以停止读取；是否实际采用该路径，需要通过执行计划验证。

当前先实现销量汇总字段和排名索引，不在每次首页请求时从订单明细执行销量聚合。上线前使用实际规模数据检查 `EXPLAIN ANALYZE`，并压测查询耗时、扫描行数、并发读写和数据库负载；目前尚未完成这些验证。

如果上线后首页访问量较高，而且业务允许榜单短暂延迟，可增加 Redis 榜单结果缓存。30 秒刷新只是讨论中的建议，尚未确定，不视为当前需求。需要频繁更新、接近实时的排行榜时，再评估 Redis Sorted Set，并处理事件去重、退款、下架、同销量排序及数据重建。

## 7. 尚待明确的业务事项

- 销量按件数还是订单数统计、累计还是时间段统计，以及支付、退款、退货的计入规则。
- 多 SKU 销量如何汇总到商品，以及多 SKU 商品的展示价格如何确定。
- 缺货商品是否参与排名。
- 商品与历史销量的真实数据来源；不得用随机销量作为真实业务数据。
- 分类表、商品参数表和 SKU 表的具体设计。
- 排行榜是否允许缓存延迟及其刷新周期。
- 首次访问时 JWT 的取得方式、签发与校验约定，以及业务失败码。商品接口已有 Result 字段与成功码约定，其他待定接口事项继续按 [需求.md](./需求.md) 中的待确认清单推进。
