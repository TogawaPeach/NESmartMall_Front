## 1. 已确认的交互与请求

1. 继续保留购物车纸质小票。点击小票“模拟支付”先调用 `POST /api/orders` 创建待付款订单，明确成功后才打开结果弹窗。
2. 弹窗继续展示创建结果中的 `data.orderNo` 和 `data.payableAmountFen`。金额是后端应付总额，单位分，按两位小数元显示；创建成功不表示付款成功。
3. 在此弹窗新增“立即支付”按钮。只有用户点击该按钮才提交支付，不因弹窗打开或订单创建成功而自动付款。
4. 弹窗“立即支付”和订单列表/详情中的继续模拟支付，统一复用同一个支付 API：`POST /api/orders/{orderNo}/pay`。
5. `orderNo` 来自已经创建或查询到的订单，保持 JW 开头的字符串，放在 URL 路径中；无需业务请求体。沿用现有 Bearer 登录凭证，不额外提交用户 ID、金额、商品或收货信息。
6. 继续支付使用原订单号，不重新创建订单。关闭弹窗或暂不支付不取消订单。

创建接口仍按已确认的两字段消费约定处理，不因本次支付需求重新要求创建返回完整 Order：`data` 只需 `orderNo` 和 `payableAmountFen`。详情数据通过已有查询接口另行取得。

## 2. 后续支付成功响应目标

用户明确不喜欢支付接口继续返回 `detail`，后续应简化为无业务数据的成功 `Result`：

```http
POST /api/orders/JW1980123456789012345/pay
Authorization: Bearer <现有登录令牌>
```

上面的订单号仅为接口格式示例，请求无业务 body。成功响应目标为 HTTP 200：

```json
{
  "code": 200,
  "message": "OK",
  "data": null
}
```

Controller 对外目标类型为 `Result<Void>`，不返回订单详情、订单号、金额、状态或其他业务字段。必须在支付 Service 正常完成后才返回成功；不是收到请求就直接返回成功。

期望的 Controller 结构如下，仅作后续修改参考，本轮未写入后端：

```java
@PostMapping("/{orderNo}/pay")
public Result<Void> pay(
        @PathVariable("orderNo") String orderNo) {

    orderPaymentService.pay(orderNo);

    return new Result<>(200, "OK", null);
}
```

Service 是否同时改为 `void`、如何保留内部状态判断，留待后续代码 review；“不向前端返回 detail”不等于直接删除内部幂等和错误判断所用查询。

## 4. 后续前端适配与验证要点

- 弹窗与订单页复用同一支付请求方法；成功校验 HTTP/业务结果，不再将缺少 `data` 中完整订单视为失败。
- 明确支付成功后显示成功提示，再通过现有订单查询刷新列表或详情。支付接口无需为页面刷新额外返回详情；后续查询失败应提示刷新失败，不应把已经明确成功的支付改判成失败。
- 支付请求期间显示处理中并防止重复点击。明确业务拒绝显示错误；超时、断网等未知结果按已知订单号查询确认，不本地伪造成功、不自动重发支付或创建订单。
- 账号切换、关闭或组件销毁后的旧响应继续隔离，避免旧订单结果影响当前账号或新操作。
- 需一并处理订单页“付款信息暂未就绪，请刷新订单”导致支付入口不可用的问题。不能把补齐旧版 `serverTime/canPay/displayStatus/cancelReason` 当成这次接口简化的隐含前提；`cancelReason` 已取消，订单是否可付最终由后端判断。前端资格提示与到期展示的具体适配留待后续实现核对。
- 创建阶段已有防重、未知结果恢复、金额分转元和异步购物车清理约定继续保留；确认支付与确认收货 `POST /api/orders/{orderNo}` 是两个独立动作。
- 后续验证应覆盖：弹窗按钮携带正确原订单号；两处入口请求一致；`data: null` 成功；重复点击防重；失败和未知结果；支付明确成功但订单刷新失败；订单页缺失旧付款字段时的入口可用性。
