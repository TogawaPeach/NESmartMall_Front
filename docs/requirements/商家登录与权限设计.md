# 商家登录与权限设计

更新时间：2026-10-14

本文承接 [需求.md](./需求.md) 的需求 002。已确认业务需求为：使用 JWT 鉴权，商家账号登录后进入商家后台，支持查看销量、上传商品、下架商品。本次账户、角色、昵称、登录契约及 JWT 选择见 [账户与登录最终约定.md](./账户与登录最终约定.md)；路由和未定字段仍为实施建议，尚未实现或执行数据库迁移。

**当前按用户选择仅解码 JWT，不验证签名，身份及角色可伪造。下文按账户 ID 过滤商品是功能规则，不能据此保证只能修改自己的商品。**

商家与需求 004 中的“商户”为同一身份。登录服务、网关、JWT 契约、Nacos 与后台入口的实施基线见 [登录服务与网关需求.md](./登录服务与网关需求.md)；本文继续细化商家商品管理及数据归属。后台页面目前尚未开发，认证与鉴权可先独立验收，页面导航和商品管理按后续阶段验收。

微服务调用、Seata、后期 RabbitMQ 和 Redis 见 [微服务基础设施与通信需求.md](./微服务基础设施与通信需求.md)。商品站内详情路径关联见 [商品详情页需求.md](./商品详情页需求.md)，商户维护时同样检查商品归属；新增表不自动要求跨服务事务。

## 1. 服务职责

沿用单仓库、Maven 多模块方案：

| 模块 | 职责 |
| --- | --- |
| mall-auth-service | 登录、验证密码、读取账户角色及昵称（商家昵称即店铺名）、签发 JWT、查询当前登录信息 |
| mall-gateway | 对外入口、路由与入口鉴权 |
| mall-product-service | 商品查询、创建、上下架，检查商品所属商家，返回商品累计销量 |
| mall-common | Result 等小型公共类型；不存放业务实体或数据库访问逻辑 |
| 前端 | 根据登录响应执行导航、身份恢复和后台路由守卫；页面跳转不能替代接口授权 |
| Nacos | 已确定为服务注册中心，配置管理分阶段接入；不处理商城登录或 JWT 签发 |

商家后台是前端页面集合，初期商品管理由商品服务提供，不因有后台页面就新建一个汇集所有业务的后端服务。时间段销量、销售额等统计在订单需求明确后再落实。

## 2. 登录与导航

1. 前端向 POST /api/auth/login 提交 account、password，不提交角色或 ID，无 JWT 时可调用。
2. 认证服务查账户、验证密码哈希与账户状态，从数据库读取角色和昵称。普通用户 role 为 1，商家为 0。
3. 登录成功返回 JWT、以秒为单位的 expiresIn（本次响应为 86400）及 user.id、user.account、user.nickname、user.role。商家昵称就是店铺名，不另建店铺名称字段。
4. 当前商城用户入口登录成功留在原页面，保留用户图标并显示昵称菜单；按 role 导航为后续目标，建议商家进入 /merchant/dashboard，普通用户进入 /，商家页面按阶段建设。
5. 业务请求通过共享 http 实例附加 Authorization: Bearer <JWT>；当前刷新从 sessionStorage 恢复尚未过期的会话，不调用当前账户接口。后续账户接口及商家页面守卫另行接入，当前前端退出仅清除本地会话，详见 [用户入口与登录状态需求.md](./用户入口与登录状态需求.md)。
6. 网关与商品服务仅解码 JWT、执行角色和归属过滤，不验签；前端展示不构成可靠的后端身份认证。

密码仅保存 PasswordEncoder 生成的哈希，登录时用 matches 验证。商家角色通过可信管理流程授予，普通注册不允许自选。具体账号创建及商家授予方式待确认。

## 3. JWT 与商品权限边界

JWT 的 sub 为账户 ID；roles 由数据库 role 映射：0 → MERCHANT，1 → CUSTOMER。商家账号的 sub 同时表示商家 ID，不另加 merchant_id 声明。JWT 还计划包含 iss、aud、iat、exp，不包含密码或密码哈希。

认证服务仍签发带签名的 JWT，但本版本网关和商品服务不验证签名。读取自定义 roles 时需明确权限映射；采用 Spring 权限名称时映射到 ROLE_MERCHANT / ROLE_CUSTOMER。标准 Resource Server 验签方案是后续安全修正建议，不能描述成当前仅解码方案已具备的保障。

商品服务执行接口和数据两类过滤：

- 解码 roles 没有 MERCHANT 时，商家接口返回 403。
- 商品查询按 merchant_id 限定为解码 sub；修改同时匹配商品 ID 和 merchant_id。不采用客户端提交的所有者参数或额外身份头。

本版本 sub 和 roles 均可被改写。只修改登录响应中的 user.role 不会修改原 JWT；但攻击者另行伪造 JWT 后，服务无法通过签名识别。因此不能承诺普通账号绝不取得商家权限，也不能承诺防住冒充其他商家的操作；即使按 sub 查库也无法证明请求人身份。

缺失、不可解析、必要字段缺失或检查发现过期的令牌返回 401 + Result；可解析但角色不足返回 403 + Result。跨商家资源在真实身份前提下建议统一 404。有效期、状态变化、退出和撤销策略待确认，不能依赖前端退出或旧令牌角色。

## 4. 数据模型补充

当前仅建 account 账户表，一个账户只有一个角色；不另建商家表、角色关联表或账户 merchant_id 字段。商家 ID 直接使用商家账户的 account.id。account.nickname 为用户昵称，商家昵称直接作为店铺名；建议昵称不要求唯一（最终规则待确认），不用于归属检查。字段类型与约束建议见最终约定第 3 节。

当前 [商品表设计与初始化约定](./商品表设计.md) 的 product 表没有商家归属，需要在实施商家管理前增加：

| 字段或索引 | 建议用途 |
| --- | --- |
| merchant_id BIGINT NOT NULL | 商品所属商家账户的 account.id；创建时由后端按解码 sub 赋值，当前身份可伪造 |
| idx_product_merchant (merchant_id, is_deleted, status, id) | 支持商家范围商品列表；实际索引根据查询与执行计划调整 |

跨服务 ID 保持逻辑关联，不要求跨库外键。若已有商品数据，先添加可空字段，按真实归属回填并验证，最后改为 NOT NULL；不能给历史商品随意指定一个默认商家。本文不改写已有建表 SQL，也不执行迁移。

创建商品时由后端初始化销量为 0、状态为草稿，商家不能提交销量、所有者或删除标记来覆盖系统字段。是否上传后直接上架、是否需要审核，待确认。

下架操作应将状态改为 2，保留商品和历史销量。首页现有 `status = 1 AND is_deleted = 0` 查询自然排除下架商品。

## 5. 接口草案

| 方法与路径 | 用途 | 权限及范围 |
| --- | --- | --- |
| POST /api/auth/login | 登录并签发 JWT | 无 JWT 可调用，验证账号密码 |
| GET /api/auth/me | 当前账户、昵称及角色 | 按解码 sub 查询，当前无法证明调用人身份 |
| GET /api/merchant/products | 商家商品列表及商品累计销量 | 商家角色，只返回自己的商品，分页查询 |
| POST /api/merchant/products | 创建商品 | 商家角色，后端绑定所有者并初始化系统字段 |
| PATCH /api/merchant/products/{id}/status | 商品上下架 | 商家角色，检查归属及允许的状态转换 |
| POST /api/merchant/uploads/images | 上传商品图片 | 商家角色，校验文件大小与类型，返回资源引用 |

“上传商品”建议拆成图片上传和商品信息提交。图片存储到文件服务或对象存储，商品表保存地址或资源标识；绑定图片时也需要检查上传资源的归属。具体存储方案待实现阶段确定。

查看销量初期可以读取自己的商品累计 `sales_count`；这不等于已有完整经营报表。每日销量、时间范围、销售额、退款扣减与 SKU 汇总需要订单事实和统一口径，不能由商家手动修改销量来生成统计。

## 6. 验收

以下为尚待实施和执行的目标验收；登录、JWT 与服务发现按需求 004 独立验收，页面导航和商品管理在对应后台功能开发后验收。

- 普通用户登录进入商城，商家登录进入商家后台；刷新页面能恢复身份。
- 无 JWT、不可解析或声明检查失败时返回 401 和 Result；篡改签名或载荷不具备拒绝保证。
- 使用原始普通用户令牌调用商家接口返回 403 和 Result；伪造商家角色令牌的情形属于当前已知缺口。
- 使用原始商家 A 令牌时，按 merchant_id 过滤不能操作 B 的商品；不信任额外所有者参数或身份头。伪造 sub 冒充 B 不在本版本可保证拒绝的范围，不能宣称已防住跨商家越权。
- 创建商品由后端绑定商家，拒绝或忽略请求中的系统字段；初始销量为 0。
- 商家下架自己的商品后，商城查询不再展示它，商家后台仍可查看记录及累计销量。
- 禁用账号或修改角色后的生效机制另行确定，不把前端退出或旧令牌作为已实现保障。
- 商家登录返回 nickname，后台按店铺名展示；商品归属始终用账户 ID，修改昵称不改变归属。
- 统计结果来自真实数据，累计销量与时间段统计口径可核验。

## 7. 待确认

商家账号如何创建或审批；昵称创建/修改入口与长度校验；角色变更后已有商品的处理；商家能否切回商城；上传商品是否需要审核；销量统计范围和退款口径；服务端 JWT 刷新与撤销方式、禁用与角色变更生效机制；图片存储方案。前端当前已使用 sessionStorage，并按实际 expiresIn 过期；商家导航尚未实现。
