# 确认收货前端实现交接

更新时间：2026-10-18

状态：前端已实现；后端接口尚未实现，真实收货状态变更仍待联调。

## 交互

- 订单列表、订单详情页仅对 `PENDING_RECEIPT` 订单开放“确认收货”。
- 点击按钮打开居中的 Element Plus Dialog，显示订单号及“请确认您已收到全部商品且检查无误。是否确认收货？”。
- 点击“取消”、关闭按钮、遮罩或 Escape 只关闭弹窗，不发送确认收货请求。
- 仅点击“同意并确认收货”后发送请求。提交中显示 loading，拦截重复提交并暂时禁止关闭。
- 业务成功后关闭弹窗、提示“确认收货成功”，重新查询当前列表（保留状态筛选）或当前详情。完成状态与完成时间来自重新查询的后端数据，不由前端补造。
- 失败时保留弹窗并展示错误；网络错误提示刷新订单确认实际结果，不自动重试。切换账号、订单或离开页面后，中止前端等待并忽略旧响应；中止等待不代表服务端撤销操作。

## 待后端实现的接口约定

用户要求去掉建议路径中的 `confirm-receipt` 后缀，因此当前前端采用：

```http
POST /api/orders/{orderNo}
Authorization: Bearer <accessToken>
Accept: application/json
```

- 同一路径的 GET 仍用于查询订单详情，POST 用于确认收货。
- 请求无业务 body，不传数据库订单主键、用户 ID、目标状态或完成时间。
- `orderNo` 沿用 `JW[1-9][0-9]{0,61}` 字符串格式，总长度不超过 64。
- 成功响应：`{ "code": 200, "message": "OK", "data": null }`。前端依据业务码 200 判断成功，不依赖 data 字段；HTTP 错误或其他业务码不会提示成功。
- 失败响应沿用 Result 结构和 message。前端兼容 HTTP 错误状态及 HTTP 200 内的失败业务码，并提供 401、403、404、409 的默认文案。
- 后端应从可信会话获取用户身份，限定当前用户与订单号，原子校验待收货状态，成功写入 `COMPLETED` 和 `completedAt`；并明确重复确认的幂等行为。
- 开发用订单查询 mock 保持只读，不模拟真实确认收货成功。本次未修改后端、数据库或运行收货写接口联调。
