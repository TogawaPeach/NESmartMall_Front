## 1. 当前 JWT 选择与安全边界

最新设计：JWT 必须验签，由 mall-gateway 本地验证并判入口角色。mall-auth-service 负责登录时检查账户、密码与状态并签发 JWT；不新增内部 verify RPC，product 不重复验 JWT。

保留 HS256，配置文本 UTF-8 经 SHA-256 得到 32 字节密钥，演示文本仍为 NESmartMall，TTL 为 86400 秒。网关使用同样的派生方法；公开演示文本只用于 demo，不构成生产安全保证。

首期离线验签不查当前账户状态。登录时禁用账户不能取得新令牌；登录后禁用、删除或改角色，旧 JWT 按签发时身份继续工作至到期，最长约一天（首期建议时钟容差 0）。本轮明确这一首期边界，不宣称即时撤权；有即时需求再设计状态/版本/撤销机制。退出仅清前端会话，refresh/logout/单设备撤销尚未实现。

已有登录签发不等于网关验证已实现；下文为待开发和待验收要求。

## 2. 服务职责与建设顺序

| 模块 | 当前设计 |
| --- | --- |
| mall-auth-service | 管理账户，校验登录参数、BCrypt 密码及状态，读取角色并签发；JSON 错误封装待补 |
| mall-gateway | 精确白名单、清除外部身份头、Bearer/JWT 本地验证、入口角色检查、覆盖内部身份和目标服务凭据 |
| mall-product-service | 验证内部请求来源，建立本服务 CurrentUser/ThreadLocal，检查接口权限和 merchant_id 归属 |
| mall-common | Result、CurrentUser/UserContext 等小型公共类型，不管理数据库或签发密钥 |
| 前端 | 保留弹窗、昵称菜单、localStorage 与 Bearer；403 提示及商家导航待接入 |

保持 gateway 8080 → auth 8081 / product 8082 的固定路由；Vite /api 代理 8080。先补 gateway 验签与访问规则，再接内部来源认证和 product 上下文；需要时才引入 Nacos、Feign。身份通过 user-info/user-role 跨服务传递，接收方恢复自己的 ThreadLocal，请求结束清理。

## 3. 账户与商家模型

### 3.1 已确认关系

- 现有数据库实际名称保留为 `nesmartmall_product`，作为商城共用数据库，不执行改名或迁库，也不另建 `nesmartmall_auth`；商品表仍叫 `product`，账户表叫 `account`。
- 账户表名称为 `account`，由认证服务管理；与商品表同库，业务访问职责仍按服务划分。
- 一个账户只有一个角色：`role = 0` 为商家，`role = 1` 为普通用户。
- 当前一个商家账号表示一个商家，不单独建立 `merchant` 表或角色关联表。
- 账户增加 `nickname` 用户昵称字段；商家账号的昵称就是店铺名，不另建 `shop_name` 或独立店铺名称字段。
- 商家 ID 直接使用商家账号的 `account.id`；`account` 表不另加 `merchant_id`。
- 商品后续增加 `product.merchant_id`，逻辑关联商家账号的 `account.id`。
- 当前主键建议沿用商品表风格，使用 `BIGINT AUTO_INCREMENT`；不额外增加 UUID。接口及 JWT 中的账户 ID 使用字符串，避免前端大整数精度丢失。

### 3.2 第一版字段方案

用户已在现有库中建立 account 表并准备测试账户；本次检查了实体和查询 XML，未连接数据库核对 DDL。字段约定如下，精确约束以实际表结构为准。

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `id` | `BIGINT` | 自增主键，永久账户标识；商家账号同时使用此值作为商家 ID |
| `account` | `VARCHAR(64)` | 必填手机号登录账号，建立唯一索引；注册时去除首尾空白并校验11位手机号，既有登录仍兼容历史账号 |
| `nickname` | `VARCHAR(64)` | 用户昵称；商家账号直接将该字段用作店铺名；建议必填且非空白，不要求全站唯一 |
| `password_hash` | `VARCHAR(255)` | 必填密码哈希，使用 BCrypt 生成，使用 `BCryptPasswordEncoder.matches` 验证；不保存明文或可逆加密密码 |
| `role` | `TINYINT` | 必填，`0` 商家、`1` 普通用户；建议默认 `1` 并约束取值 |
| `status` | `TINYINT` | 已有字段：`0` 禁用、`1` 正常，默认 `1`；注册请求不传，不修改默认值 |
| `created_at` | `DATETIME(3)` | 注册时间，建议默认当前时间 |
| `updated_at` | `DATETIME(3)` | 建议补充：最后修改时间 |
| `last_login_at` | `DATETIME(3)` | 建议补充：最近成功登录时间，未登录时为空 |

昵称仅用于展示，不用于登录唯一性、JWT 角色判定或商品归属。建议允许昵称和店铺名重名，最终唯一性规则待确认；商品归属仍使用永久账户 ID；昵称变更不改变 ID。`VARCHAR(64)`、非空要求以及昵称创建/修改入口为实施建议，具体规则待确认。

2026-10-14 注册约定更新：注册时允许选择普通用户（role=1，默认）或商家（role=0），后端校验角色只能为 0 或 1 后创建账号。账号 account 为手机号，nickname 为昵称（商家即店铺名），接口接收原始 password，后端 BCrypt 后写入 password_hash；status 保留已有默认 1，前端不传。注册成功返回登录，不自动签发 JWT。前端已完成，后端注册接口和精确白名单待实现，详见 [注册功能需求与前端实现交接.md](./注册功能需求与前端实现交接.md)。账户表不保存 JWT 字符串。

## 4. 登录请求与响应

### 4.1 点击登录

未登录时点击商城顶部用户入口，在当前页面打开登录弹窗。用户填好账号和密码后，前端经网关发送：

```http
POST /api/auth/login
Content-Type: application/json
```

```json
{
  "account": "zhangsan",
  "password": "用户输入的密码"
}
```

登录请求不需要 JWT，不提交角色、账户 ID 或商家 ID。当前本地求职 demo 使用 HTTP，前端不另加密密码；本地开发由 Vite 转发到 `http://localhost:8080/api/auth/login`。正式部署再配置 HTTPS。该登录路径已用普通用户账号完成浏览器联调，注册前端已实现、后端注册待联调，找回密码尚未接入。前端只去除账号首尾空白，密码原样放入 JSON body，不发送角色或用户 ID。

### 4.2 认证服务处理

1. Controller 已校验账号和密码 null / 空白并返回 HTTP 400 和失败 `Result`；缺少请求体、JSON 格式或类型错误的统一 Result 处理尚需补齐。
2. 根据 `account` 查询账户表。
3. 用 `PasswordEncoder.matches` 验证密码哈希，并检查账户状态。
4. 账号或密码错误使用统一提示，返回 HTTP 401 和失败 `Result`；禁用账号不得取得新令牌。
5. 从数据库读取 `id`、`account`、`nickname`、`role`，不采用客户端指定的角色。
6. 映射 JWT 角色并签发令牌，返回成功结果；当前未更新 last_login_at。

### 4.3 普通用户登录成功

HTTP 200；响应示例：

```json
{
  "code": 200,
  "message": "OK",
  "data": {
    "accessToken": "签名后的JWT字符串",
    "tokenType": "Bearer",
    "expiresIn": 86400,
    "user": {
      "id": "10001",
      "account": "zhangsan",
      "nickname": "张三",
      "role": 1
    }
  }
}
```

`expiresIn` 单位为秒，本次提供并联调的响应为 `86400`（24 小时）；前端按每次实际返回值计算过期时间，不硬编码 24 小时。该响应不表示刷新令牌、服务端撤销或账户禁用生效策略已经实现。商家登录使用相同结构，`user.role = 0`，`user.nickname` 为店铺名。不再使用早期 `user.roles` 和 `user.merchantId` 响应草案；JWT 内部继续使用 `roles` 数组。

当前用户入口登录成功关闭弹窗并留在原页面，用户图标保留，桌面显示 `user.nickname`；昵称为空时回退显示账号，点击菜单查看昵称、账号并退出。角色导航的后续目标为普通用户进入商城、商家进入后台，当前未实现商家导航。`/` 与 `/merchant/dashboard` 为建议页面路径，后台页面尚未建立时，跳转不可视为已完成验收。修改响应或前端保存的 `user.role` 只能改变页面状态，不能作为授权依据。目标方案由 gateway 本地验签和判定入口角色；目前该检查还未接入。

### 4.4 后续请求与身份恢复

业务请求统一附带：

```http
Authorization: Bearer <JWT>
```

当前前端在 `localStorage` 的 `nesmartmall.auth` 中仅保存 `accessToken`、`tokenType`、`expiresAt` 和 `user`；不保存账号密码请求对象或密码。`expiresAt = 登录成功时的 Date.now() + expiresIn × 1000`。刷新时检查存储结构和过期时间，恢复同源各标签页的展示状态，不重复发送登录请求，也不调用 `/api/auth/me`。

业务请求通过共享 `http` 实例时，以 `Authorization: Bearer <accessToken>` 传递令牌，不在 body 或 URL 中发送密码、整个 user 或 expiresIn。只要当前会话有未过期 token，登录、公开首页和普通业务 API 均由共享请求层自动携带；本项目后端的绝对地址及配置的 VITE_API_BASE_URL 同样适用，第三方地址不携带。前端到期清理会话；受保护请求返回 HTTP 401 或业务 `code: 401` 时，仅在该请求携带当前令牌的情况下清理，避免旧请求影响新会话。用户再次点击用户入口重新登录，不自动弹出登录框，不自动刷新令牌或重试。

退出登录清除同源共享的前端会话并同步其他标签页；关闭标签页或浏览器后，未过期会话仍可恢复。不调用尚未提供的注销接口，也不表示服务端已撤销 JWT。存储不可用时仍允许本次页面内存登录，刷新恢复不保证。

`GET /api/auth/me` 保留为后续获取最新账户信息的接口方案，目前后端未实现、前端未接入。实现时必须使用 gateway 验证并经可信内部调用传来的身份查询数据库。详情和验收记录见 [用户入口与登录状态需求.md](./用户入口与登录状态需求.md)。

## 5. JWT 角色与接口过滤

当前签发约定：算法 HS256；`iss = NESmartMall`；`aud = ["nesmartmall-api"]`；`sub` 为字符串账户 ID；包含 `iat`、`exp` 和 `roles`，不包含密码或密码哈希。数据库 `role = 0` 映射 `["MERCHANT"]`，`role = 1` 映射 `["CUSTOMER"]`。采用 Spring 权限名称时再映射 ROLE_MERCHANT / ROLE_CUSTOMER。

目标由 gateway 限制 HS256，验证签名、issuer、audience、时间及必需声明，从已验证的 sub/roles 取得身份。首期不每请求查询账户，角色变更与禁用生效边界见第 1 节；具体声明验证、公开链路隔离和角色映射见跨 Harness 文档。

| 方法与路径 / 场景 | 最新访问规则（待接入） |
| --- | --- |
| `POST /api/auth/login` | 公开，验证账号密码 |
| `GET /api/products` | 公开，首页含分类筛选的销量前八；服务端强制最多八条 |
| `GET /api/products/page` | 必须登录，包含分页及 keyword 搜索 |
| 订单、购物车接口 | 必须登录；具体 API 尚未设计，不表示已有实现 |
| `/api/merchant/**` | 必须登录且当前账户为商家；商品服务另检查归属 |
| `GET /api/auth/me` | 将来实现时必须登录 |
| CORS OPTIONS | 按实际 CORS 策略放行预检 |
| 受保护请求缺少令牌、验签/声明失败 | HTTP 401 + `Result.code = 401` |
| 有效身份但接口角色不足 | HTTP 403 + `Result.code = 403` |
| 目标服务不可用、转发超时或内部故障 | 明确 5xx，不伪装成 401，不清除正常会话；auth 停止不阻塞已有有效 JWT 访问正常 product |

白名单按方法和精确路径匹配，不整体公开 `/api/auth/**` 或 `/api/products/**`；查询参数不把分页路径变成公开接口。公开首页无需 token，过期 token 不应使其不可访问，后续可让前端省略公开请求的 token，并让网关公开规则不强制校验它。未知接口默认受保护，新增路由同步更新权限规则。

前端点击订单、购物车、查看全部和搜索时先判断登录状态，未登录提示登录；后端仍独立校验，直接构造请求也不能绕过。当前前端已有登录能力，这些点击拦截尚待新增。首页查询 limit 当前直接传入 Mapper，服务端上限也尚待补齐。

## 6. 商品归属

商品服务后续增加 `product.merchant_id`，其值为商家账号的 `account.id`，不关联独立商家表，也不要求跨库外键。若已有商品数据，先添加可空字段并按真实归属回填，再根据数据决定非空约束，不任意指定默认商家。

创建商品时，由后端将 gateway 本地验证通过且经可信内部链路传递的账户 ID 写入 `merchant_id`，不允许前端任意指定所有者。商家列表按 `merchant_id` 过滤；修改、上下架应同时限定商品 ID 与账户 ID，例如：

```sql
UPDATE product
SET status = #{status}
WHERE id = #{productId}
  AND merchant_id = #{currentAccountId};
```

上述为 Mapper 条件示意，不是本次执行的数据库脚本。`currentAccountId` 来自 gateway 本地验证通过的身份上下文，禁止直接相信客户端提交的账户 ID 或额外身份头。网关入口鉴权不替代商品服务的资源归属检查；这两部分目前都尚未实现。未来若要记录具体上传者，可另加 `created_by`，当前无需增加。
