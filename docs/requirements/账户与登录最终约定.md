# 账户与登录最终约定

更新时间：2026-10-14\
文档状态：账户模型约定已整理；2026-10-14 已完成前端用户登录弹窗、Bearer 传递和刷新恢复，并验证普通用户真实登录。本文不表示已审查后端账户表、密码哈希实现或执行数据库迁移。

本文是本次账户模型、登录请求与响应、角色判定及 JWT 处理方式的当前约定。与早期文档不一致时，以本文及同步更新后的登录、商家文档为准。

## 1. 当前 JWT 选择与安全边界

本次用户明确选择：**后端只解码 JWT、读取身份与角色，不验证 JWT 签名。** 登录时认证服务仍签发带签名的 JWT，但网关与业务服务不使用签名确认令牌来源。

**这不是可信的身份认证方案。** 未验签的 `sub` 和 `roles` 都是请求方可伪造的数据。修改 JWT 中的角色可以冒充商家，修改账户 ID 可以冒充其他账户；即使 SQL 带商品归属条件，也不能保证商家只能操作自己的商品。检查格式、有效期、签发者或受众，也不能替代验签，因为这些声明同样可以被改写。

因此本版本不能继续采用早期“篡改签名必然返回 401”“改角色不能获得商家权限”“可以防止跨商家修改”的安全验收结论。下文将正常角色与归属过滤流程和伪造令牌的已知缺口分别记录，不宣称已满足安全鉴权。恢复验签作为后续修正建议，不在本次文档中静默替换用户选择。

## 2. 服务职责与建设顺序

| 模块 | 本次约定 |
| --- | --- |
| `mall-auth-service` | 管理账户，验证账号密码与状态，查询数据库角色，签发 JWT，提供当前账户信息；后续刷新、退出与撤销策略在此服务落实 |
| `mall-gateway` | 浏览器统一入口；转发登录请求，解析业务请求的 Bearer JWT，按解码角色执行入口过滤；本版本不验签 |
| `mall-product-service` | 按解码角色限制商家接口，按解码账户 ID 限定商品范围；本版本不验签，身份来源不可信 |
| `mall-common` | 放置 `Result` 等小型公共类型，不管理账户持久化或签发私钥 |
| 前端 | 已实现用户入口登录弹窗、昵称菜单、sessionStorage 恢复和统一附加 Bearer JWT；商家导航待实现，页面角色不能作为后端授权依据 |

先使用现有固定地址路由打通登录链路：网关 8080 → 认证服务 8081 / 商品服务 8082。Nacos 仍保留为整体注册中心选型，登录开发不以先接入 Nacos 为前提。后续接入注册发现及负载均衡，再切换到 `lb://mall-auth-service`、`lb://mall-product-service`。

前端开发代理已将 `/api` 统一代理到网关 8080，登录使用相对路径 `/api/auth/login`，无需在页面硬编码后端地址。登录本身不要求同时接入 Feign、Seata、RabbitMQ 或 Redis。

## 3. 账户与商家模型

### 3.1 已确认关系

- 现有数据库实际名称保留为 `nesmartmall_product`，作为商城共用数据库，不执行改名或迁库，也不另建 `nesmartmall_auth`；商品表仍叫 `product`，账户表叫 `account`。
- 账户表名称为 `account`，由认证服务管理；与商品表同库，业务访问职责仍按服务划分。
- 一个账户只有一个角色：`role = 0` 为商家，`role = 1` 为普通用户。
- 当前一个商家账号表示一个商家，不单独建立 `merchant` 表或角色关联表。
- 账户增加 `nickname` 用户昵称字段；商家账号的昵称就是店铺名，不另建 `shop_name` 或独立店铺名称字段。
- 商家 ID 直接使用商家账号的 `account.id`；`account` 表不另加 `merchant_id`。
- 商品后续增加 `product.merchant_id`，逻辑关联商家账号的 `account.id`。
- 当前主键建议沿用商品表风格，使用 `BIGINT AUTO_INCREMENT`；不额外增加 UUID。接口及 JWT 中的账户 ID 使用字符串，避免前端大整数精度丢失。

### 3.2 第一版字段方案

核心业务字段为账号、用户昵称（商家店铺名）、密码哈希、注册时间、角色和主键；以下类型及辅助字段为本次整理的建议，落建表前按实际数据库核对。

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `id` | `BIGINT` | 自增主键，永久账户标识；商家账号同时使用此值作为商家 ID |
| `account` | `VARCHAR(64)` | 必填登录账号，建立唯一索引；账号格式、大小写与空白规范待确认 |
| `nickname` | `VARCHAR(64)` | 用户昵称；商家账号直接将该字段用作店铺名；建议必填且非空白，不要求全站唯一 |
| `password_hash` | `VARCHAR(255)` | 必填密码哈希，通过 `PasswordEncoder` 生成，使用 `matches` 验证；不保存明文或可逆加密密码 |
| `role` | `TINYINT` | 必填，`0` 商家、`1` 普通用户；建议默认 `1` 并约束取值 |
| `status` | `TINYINT` | 建议补充：`0` 禁用、`1` 正常，默认 `1` |
| `created_at` | `DATETIME(3)` | 注册时间，建议默认当前时间 |
| `updated_at` | `DATETIME(3)` | 建议补充：最后修改时间 |
| `last_login_at` | `DATETIME(3)` | 建议补充：最近成功登录时间，未登录时为空 |

昵称仅用于展示，不用于登录唯一性、JWT 角色判定或商品归属。建议允许昵称和店铺名重名，最终唯一性规则待确认；商品归属仍使用永久账户 ID；昵称变更不改变 ID。`VARCHAR(64)`、非空要求以及昵称创建/修改入口为实施建议，具体规则待确认。

账号创建流程不接受客户端自行授予商家角色；普通注册若开放，由后端固定赋予角色 `1`。商家账号的创建或审批方式待确认。头像、手机、邮箱按实际功能再补；账户表不保存 JWT 字符串。

## 4. 登录请求与响应

### 4.1 点击登录

未登录时点击商城顶部用户入口，在当前页面打开登录弹窗。用户填好账号和密码后，前端经网关发送：

```http
POST /api/auth/login
Content-Type: application/json
```

```json
{
  "account": "zhangsan",
  "password": "用户输入的密码"
}
```

登录请求不需要 JWT，不提交角色、账户 ID 或商家 ID。生产接口通过 HTTPS 传输；本地开发由 Vite 转发到 `http://localhost:8080/api/auth/login`。该登录路径已用普通用户账号完成浏览器联调，注册和找回密码尚未接入。前端只去除账号首尾空白，密码原样放入 JSON body，不发送角色或用户 ID。

### 4.2 认证服务处理

1. 校验必填参数，缺失、空值或类型不正确时返回 HTTP 400 和失败 `Result`。
2. 根据 `account` 查询账户表。
3. 用 `PasswordEncoder.matches` 验证密码哈希，并检查账户状态。
4. 账号或密码错误使用统一提示，返回 HTTP 401 和失败 `Result`；禁用账号不得取得新令牌。
5. 从数据库读取 `id`、`account`、`nickname`、`role`，不采用客户端指定的角色。
6. 映射 JWT 角色并签发令牌，返回成功结果；可记录成功登录时间。

### 4.3 普通用户登录成功

HTTP 200；响应示例：

```json
{
  "code": 200,
  "message": "OK",
  "data": {
    "accessToken": "签名后的JWT字符串",
    "tokenType": "Bearer",
    "expiresIn": 86400,
    "user": {
      "id": "10001",
      "account": "zhangsan",
      "nickname": "张三",
      "role": 1
    }
  }
}
```

`expiresIn` 单位为秒，本次提供并联调的响应为 `86400`（24 小时）；前端按每次实际返回值计算过期时间，不硬编码 24 小时。该响应不表示刷新令牌、服务端撤销或账户禁用生效策略已经实现。商家登录使用相同结构，`user.role = 0`，`user.nickname` 为店铺名。不再使用早期 `user.roles` 和 `user.merchantId` 响应草案；JWT 内部继续使用 `roles` 数组。

当前用户入口登录成功关闭弹窗并留在原页面，用户图标保留，桌面显示 `user.nickname`；昵称为空时回退显示账号，点击菜单查看昵称、账号并退出。角色导航的后续目标为普通用户进入商城、商家进入后台，当前未实现商家导航。`/` 与 `/merchant/dashboard` 为建议页面路径，后台页面尚未建立时，跳转不可视为已完成验收。修改响应或前端保存的 `user.role` 只改变页面状态；本版本另有 JWT 本身可伪造的缺口，不能据此宣称后端商家权限可靠。

### 4.4 后续请求与身份恢复

业务请求统一附带：

```http
Authorization: Bearer <JWT>
```

当前前端在 `sessionStorage` 的 `nesmartmall.auth` 中仅保存 `accessToken`、`tokenType`、`expiresAt` 和 `user`；不保存账号密码请求对象或密码。`expiresAt = 登录成功时的 Date.now() + expiresIn × 1000`。刷新时检查存储结构和过期时间，恢复当前标签页的展示状态，不重复发送登录请求，也不调用 `/api/auth/me`。

业务请求通过共享 `http` 实例时，以 `Authorization: Bearer <accessToken>` 传递令牌，不在 body 或 URL 中发送密码、整个 user 或 expiresIn。登录接口不自动附加旧令牌，绝对地址请求不自动附加令牌。前端到期清理会话；受保护请求返回 HTTP 401 或业务 `code: 401` 时，仅在该请求携带当前令牌的情况下清理，避免旧请求影响新会话。用户再次点击用户入口重新登录，不自动弹出登录框，不自动刷新令牌或重试。

退出登录仅清除当前标签页的前端会话，关闭标签页后该会话结束；不调用尚未提供的注销接口，也不表示服务端已撤销 JWT。新标签页之间不做登录状态同步。存储不可用时仍允许本次页面内存登录，刷新恢复不保证。

`GET /api/auth/me` 保留为后续获取最新账户信息的接口方案，当前前端尚未接入。它可以按解码 `sub` 查询数据库，但因为 `sub` 未经验签，仍不能确认请求人就是该账户。详情和验收记录见 [用户入口与登录状态需求.md](./用户入口与登录状态需求.md)。

## 5. JWT 角色与接口过滤

数据库角色与 JWT 映射约定：

| 数据库 `role` | JWT `roles` | Spring 权限映射（若使用） |
| --- | --- | --- |
| `0` | `["MERCHANT"]` | `ROLE_MERCHANT` |
| `1` | `["CUSTOMER"]` | `ROLE_CUSTOMER` |

JWT 身份字段示例：

```json
{
  "sub": "10001",
  "roles": ["CUSTOMER"]
}
```

完整载荷还计划包含 `iss`、`aud`、`iat`、`exp`，具体值及有效期待确认；不携带密码或密码哈希。商家 ID 由商家角色下的 `sub` 表示，无需另传 `merchant_id` 声明。

本版本网关与业务服务只解码载荷，检查所需字段的格式，读取 `roles` 并按接口规则过滤；计划保留过期时间等声明检查，但它们无法证明真实性。签发算法与密钥仍待确定，不因“不验签”而改写成采用 `alg=none`；现成 Resource Server 的标准验签配置属于后续安全修正方案，不能把它与本版本的仅解码处理混写成已实现配置。

| 请求或情形 | 当前功能规则 |
| --- | --- |
| `POST /api/auth/login` | 无 JWT 可调用，验证账号密码 |
| `GET /api/auth/me`、商品读取接口 | 要求携带符合解码与字段规则的 JWT；首页首次无令牌流程待确认 |
| `/api/merchant/**` | 解码角色包含 `MERCHANT`；商品服务继续按 `sub` 过滤商品范围 |
| CORS `OPTIONS` 预检 | 按跨域配置放行，不要求 JWT |
| 缺失、无法解析、缺少必要字段或检查发现过期的令牌 | HTTP 401 + 失败 `Result` |
| 令牌可解析但角色不足 | HTTP 403 + 失败 `Result` |
| 修改 JWT 的 `roles`、`sub` 或签名后仍符合解析与声明规则 | 本版本没有签名校验拒绝保证，可能冒充商家或其他账户 |

登录白名单按方法与精确路径设置，不放行全部 `/api/auth/**`。不信任额外的客户端身份头或商品所有者参数，但这并不能补上 JWT 身份可伪造的问题。

## 6. 商品归属

商品服务后续增加 `product.merchant_id`，其值为商家账号的 `account.id`，不关联独立商家表，也不要求跨库外键。若已有商品数据，先添加可空字段并按真实归属回填，再根据数据决定非空约束，不任意指定默认商家。

创建商品时，由后端将解码身份的账户 ID 写入 `merchant_id`，不允许前端任意指定所有者。商家列表按 `merchant_id` 过滤；修改、上下架应同时限定商品 ID 与账户 ID，例如：

```sql
UPDATE product
SET status = #{status}
WHERE id = #{productId}
  AND merchant_id = #{currentAccountId};
```

上述为 Mapper 条件示意，不是本次执行的数据库脚本。`currentAccountId` 来自 JWT 的 `sub`；**在当前不验签的选择下，这个值可以被伪造，条件本身无法构成可靠的数据权限保护**。未来若要记录具体上传者，可另加 `created_by`，当前无需增加。
