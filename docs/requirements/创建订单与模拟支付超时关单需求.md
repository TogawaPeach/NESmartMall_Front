# 创建订单与模拟支付超时关单需求

更新时间：2026-10-19

状态：业务规则已确认，2026-10-19 前端已按交接契约实现并完成显式开发模拟验收。后端交易接口、表结构与 RabbitMQ 链路仍未实现；未执行 SQL、部署或真实交易联调。最终接口与前端验证以《订单创建与模拟支付前端开发交接》第 7 节及前端验证记录为准。

本日最新调整：本期不使用 UUID、Idempotency-Key 或预申请订单号。创建结果未知时不重发创建请求，提示刷新购物车并查看“我的订单”；下单时扣减可售库存，超时取消回补，订单号使用 Hutool。用户确认在小票内填写收货姓名、手机号和地址。开发顺序为先完成前端，再由用户另开会话逐步完成后端。前端先行接口契约、验收及可复制提示词见[订单创建与模拟支付前端开发交接](./订单创建与模拟支付前端开发交接.md)。

## 1. 目标与已确认结论

点击购物车纸质小票中的“模拟支付”时，先由后端创建待付款订单，创建成功后再让用户确认是否模拟支付。支付仍为演示，不连接支付渠道、不实际扣款；订单及付款状态由后端持久化，不能继续只在前端切换成功状态。

- 支付有效期统一为创建订单后的 **15 分钟**，到期通过 RabbitMQ 触发超时取消，不再采用“15 分钟停止支付、20 分钟才触发取消”的固定缓冲。
- 原先预留 5 分钟主要为避免支付与取消同时发生；改由同一订单的数据库原子条件更新和事务保证互斥，不用时间错开代替并发控制。
- 超时订单仍可查询，不能按创建时间从列表或详情隐藏。是否可查与是否可支付分开判断。
- RabbitMQ 负责触发到期关单，数据库状态和截止时间决定支付资格。消息延迟、重复或暂时不可用不能延长支付期限。
- 当前为后端模拟支付，不接微信、支付宝等真实渠道；真实支付回调、渠道查单与关单、对账另行设计。
- 创建请求本期不建设幂等键机制，采用按钮防重复提交、未知结果不重提、从订单页恢复。此选择不保证刷新、跨标签页或其他客户端重复提交只生成一笔订单；不能宣称订单号唯一约束已解决重复下单。

本文取代此前“确认支付仅前端成功、不创建订单、不发交易写请求”的后续建设约定。旧文档的实现和验收记录继续代表当时版本，不代表本次需求已经实现。

## 2. 小票、创建订单与确认支付

1. 点击购物车“结算”只打开现有纸质小票，此时不创建订单；用户在小票内填写并确认收货姓名、手机号和完整地址。
2. 点击小票“模拟支付”，前端通过基础校验后请求后端创建订单；创建中阻止重复提交，不允许提前确认支付。
3. 后端按可信当前用户和本次选择条目获取权威商品信息、重新计价，保存订单主表、商品成交快照和收货信息快照。未选商品不参与下单。
4. 创建订单时扣减商品可售库存；订单与明细使用本地事务，跨订单服务和商品服务的创建与扣库存使用短时 Seata 全局事务共同成功或回滚。全局提交成功后返回订单号、成交金额和支付截止时间，再展示支付确认弹窗。不能持有事务等待用户确认支付。
5. 弹窗以已创建订单的金额展示“这些商品总价为 ¥___，是否支付？”，不能把独立 `GET /api/cart` 查询成功当作下单成功。订单创建后的价格以成交快照为准，不随购物车或当前商品价格变化。
6. 点击“是，确认支付”请求后端模拟支付，收到明确成功结果后才显示“支付成功”。创建或支付失败不得回退旧金额假装成功。
7. 点击“否，暂不支付”、关闭弹窗或关闭小票，只退出支付操作，不自动撤销已经创建的订单。提示用户可在期限内通过“我的订单”继续支付。

所有请求沿用网关认证与可信用户上下文，前端不能指定当前用户 ID、成交价格、总金额或订单状态。对外订单号沿用 `JW` 加雪花 ID 十进制字符串，不暴露主表内部 ID。金额为安全范围内的整数分，合法 0 元订单可模拟支付，未付款与 0 元已付款必须区分。

### 2.1 不使用创建幂等键的本期恢复规则

- 前端不生成下单 UUID，不发送 Idempotency-Key 或同义业务请求键；后端本期不新增创建请求幂等表，也不新增预发订单号接口。
- 点击后立即锁定创建入口，同一页面当前创建流程最多保留一个在途创建请求。超时、断网、取消请求或无法确认事务结果时，按“下单结果暂未确认，请刷新购物车并查看‘我的订单’”处理，不能自动重发或提供直接“重试下单”按钮。
- 5xx、网关超时以及成功响应丢失或格式异常不能直接断言未创建；后端、网关、Feign 和前端也不能无约束重放创建/扣库存业务调用。Seata 的事务恢复与消息消费者幂等仍保留，不因本条取消。
- 只有明确业务拒绝且能够确认没有提交订单时，才允许用户修正后重新提交；具体错误码在前端先行交接中约定。
- 已拿到订单号后，暂不支付再打开确认框、继续支付和支付结果查询均复用该订单，不重新调用创建接口，不重置期限。订单页面提供继续模拟支付入口。
- 关闭小票、普通刷新购物车或选择变化不能把创建中、结果未知的流程直接重置成可立即重提。同一会话应保留恢复提示；退出或切换账户清理该账户的显示状态并隔离旧响应。
- 购物车是否清空不是创建结果的判断依据：订单创建成功、购物车异步清理尚未完成时，商品可能仍在购物车。应通过订单页查看后端持久化事实，不能仅凭商品还在就认定失败并再次下单。
- 刷新或跨标签页的完整防重不属于本期保证；用户明确发起另一笔购买时可创建新订单，历史订单仍保留。前端任何拦截都不能冒充服务端严格幂等。
- 关闭页面、取消前端请求或切换账户不保证后端已回滚；前端忽略迟到响应，后端保留已创建事实。

### 2.2 Hutool 订单号

- 已选择现有 Hutool 5.8.47 的 Snowflake；订单服务通过单例 OrderNoGenerator 复用生成器，返回 JW 加雪花 ID 十进制字符串，不自行重写雪花算法。
- workerId、datacenterId 从配置读取，多进程实例保证组合唯一；明确时钟回拨、重启后节点复用及异常策略。生成失败不回退为时间戳、随机数或覆盖已有订单。
- 保留数据库 order_no 唯一约束。带 JW 前缀的生成组件属于订单业务，先放 mall-order-service，不把业务前缀规则放进 mall-api 或 mall-common。

## 3. 支付期限与现有状态模型

### 3.1 截止时间

- 创建时固定 `pay_expire_at = created_at + 15 分钟`，对外返回 `payExpireAt`。重开弹窗、继续支付和消息补发均不得延长期限。
- 使用可信服务端时间校验，数据库继续按 UTC、毫秒精度写读；接口返回带时区 ISO 8601，页面按 Asia/Shanghai 显示。
- 严格边界：当前时间小于截止时间才允许支付；大于或等于截止时间拒绝支付。
- 前端结合 `serverTime` 和 `payExpireAt` 展示倒计时，到期禁用支付并重新查询；设备时间和按钮状态不能作为支付接口的授权依据。

### 3.2 状态及展示

持久化状态仍是 0 待付款、1 待发货、2 待收货、3 已完成、4 已取消，对外仍为 PENDING_PAYMENT / PENDING_SHIPMENT / PENDING_RECEIPT / COMPLETED / CANCELLED。

| 数据库事实与时间 | 页面显示 | canPay |
| --- | --- | --- |
| 状态 0，尚未到期 | 待付款及剩余时间 | true |
| 状态 0，已经到期 | 支付已超时，订单关闭处理中 | false |
| 状态 4 | 已取消；超时取消说明支付超时 | false |
| 状态 1、2、3 | 沿用对应订单状态 | false |

模拟支付成功是 0 → 1，超时取消是 0 → 4。不新增持久化的 PAID、PAYMENT_EXPIRED 或“关闭中”状态；不能照搬讨论里的字符串 SQL 示例替换现有数字状态码。

超时关闭中是后端根据事实和时间计算的展示状态；不能伪造 `cancelledAt`，不能在取消事务成功前展示已取消。

## 4. 支付与取消的并发控制

### 4.1 模拟支付

- 按可信当前用户和 orderNo 定位订单，不属于当前用户与不存在均按不可见处理。
- 数据库原子条件更新只允许“仍为状态 0 且未到截止时间”的订单变为状态 1，同时写入付款时间和实付金额；金额取该订单保存的应付金额，不接受前端覆盖。
- 依据影响行数判断是否获得状态迁移资格，禁止先查待付款、再无条件更新。
- 影响行数为 0 时重新读取并区分：同单已支付则幂等返回已支付结果；到期但未关单则明确拒绝支付；已取消则拒绝；不可见则统一 404。不能把任意未更新情况当作支付成功。
- 状态、`paid_at`、`paid_amount_fen` 等关联数据库写入在同一事务中提交；失败整体回滚，不重复记录支付副作用。

### 4.2 超时取消

- 消费者依据数据库当前事实判断，不因收到消息就直接取消。
- 只允许“仍为状态 0 且当前时间大于或等于截止时间”的订单变为状态 4，写入实际取消时间和原因 `PAYMENT_TIMEOUT`。
- 已支付、已发货、已完成或已取消的订单跳过本次取消。提前到达的消息不能取消未到期订单，需重新安排剩余等待或可靠补偿，不能 ACK 后失去后续关单机会。
- 只有取得状态迁移资格的处理才能执行取消副作用；重复消息或扫描不能重复回补库存、释放资源。

### 4.3 互斥及事务范围

支付与取消竞争同一订单行，数据库协调带旧状态的原子更新，两者最多一个成功取得 0 → 目标状态的迁移资格。支付先提交则取消跳过；取消先提交则支付拒绝。任一事务回滚后以实际提交事实为准。

事务保持短小，不能持锁或打开全局事务等待用户点击或延迟消息。订单内相关写入使用本地事务；涉及商品服务库存写入时沿用已规划的 Seata 协调，不能声称本地事务可以回滚其他服务提交。

本期选择下单扣减可售库存、取消回补，不另建预占库存模型。商品服务使用带 product_id、可售状态和 stock >= quantity 条件的原子扣减，并校验正整数数量、每项影响行数。多商品任一失败整笔下单回滚，统一更新顺序以减少死锁。支付成功不再次扣库存；超时取消按订单实际扣减量回补一次，不能因消息重复或创建事务已回滚而多加库存。先使用 MySQL InnoDB 条件更新和事务，不为防止负库存额外加入 Redis 分布式锁；后续吞吐优化以压测为依据。

## 5. RabbitMQ 与可靠关单

- 创建提交成功后，可靠安排在原支付截止时间触发的关单消息；若下单参与 Seata，须等待全局提交成功，不能只在分支本地提交后发送。
- 消息携带可追踪事件标识、订单标识和原截止时间；当前状态、归属和截止时间以数据库为准，不使用消息里的旧状态直接覆盖订单。
- 沿用基础设施“不额外安装延迟插件”的准备方向，后续细化 TTL、死信路由和消费队列。消息补发或发送延迟不得从补发时重新给予用户 15 分钟。
- 创建提交与消息发送之间须有持久化待投递记录或等价可恢复机制，覆盖创建成功后进程崩溃、发送失败与确认未知；具体实现随开发方案确定。
- 消费事务成功后确认消息，失败可重试并可追踪恢复；已支付或已取消的重复消息可幂等无操作确认。
- 配套扫描状态 0 且已到期订单，复用同一关单业务，兜底消息漏投、积压与消费者停机。扫描与消息并发也不能重复取消。
- 15 分钟是支付截止及关单触发目标，不保证消费者恰好在该时刻完成处理。第 16 分钟即使消费者未恢复，支付仍必须拒绝，查询仍须可见。

购物车由后端处理：本期按用户“刷新购物车、查看待付款订单”的流程，将订单创建全局提交成功后的已下单条目交给 RabbitMQ 异步清理，不等待用户付款。创建全局失败不发有效清理事件，前端不自行发 DELETE、不本地删除行。消息需关联本次购买快照和条目版本，不能误删后来新增或修改的商品；具体消息字段和消费者方式在后端阶段细化。未收到消息或清理失败时，订单仍然成立，不能用购物车状态代替订单状态。超时取消回补库存，不自动恢复购物车。

## 6. 查询与前端响应增量

现有 `GET /api/orders`、`GET /api/orders/{orderNo}` 继续按当前用户隔离，列表 data 仍为数组、不分页、不暴露主表内部 ID。详情继续返回商品成交快照、完整金额时间及脱敏收货信息。

列表、详情及交易成功响应需要提供或复用：

| 字段 | 约定 |
| --- | --- |
| status | 现有五种持久化状态对应的英文值 |
| payExpireAt | 固定支付截止时间；历史数据按第 7 节迁移 |
| serverTime | 本次响应使用的服务端时间，供倒计时参考 |
| canPay | 后端根据状态与期限计算的资格快照，支付接口仍独立校验 |
| displayStatus | 未超时待付款为 PENDING_PAYMENT；超时未取消为 PAYMENT_EXPIRED；其他沿用 status |
| cancelReason | 未取消或历史原因未知可为 null；本次超时取消为 PAYMENT_TIMEOUT |

- 不增加“仅返回创建 15 分钟之内未付款订单”的查询条件，超时不返回 404。
- 筛选仍按持久化 status：超时未关单仍可出现在待付款筛选，但显示超时并禁用支付；取消提交后才进入已取消。“全部”和详情始终保留这笔订单。
- 不新增超时筛选标签，前端不能把 displayStatus 当作新的持久化状态而报非法订单。
- 订单页提供尚可支付订单的继续模拟支付入口，复用同一订单，不要求返回购物车重新创建。
- 请求失败或结果未知展示失败或恢复状态，不本地补造支付成功；切换账户清空旧状态并隔离迟到响应。
- 原小票“不会生成订单”说明必须更新，例如“将创建订单，模拟支付不会实际扣款”。

## 7. 数据设计增量

- 继续使用 `mall_order` 和现有状态 0～4，新增固定 `pay_expire_at`，类型为 DATETIME(3)，新订单必填。
- 新增可空 `cancel_reason`，本次超时取消用 PAYMENT_TIMEOUT；未取消或历史原因未知不编造原因。
- 按扫描需要评估 `(status, pay_expire_at, id)` 索引，保留现有订单号唯一与用户排序索引。
- 本期不新增创建请求 UUID 字段或幂等表；订单号唯一约束继续保留。支付状态迁移、库存回补和消息消费的幂等不受影响。
- 实施时明确历史期限回填和任务启用顺序，避免旧待付款订单因缺期限而永久可支付；不能重置历史创建时间或从迁移时重新延长 15 分钟。
- 取消不改写商品成交快照；关闭处理中不填实际取消时间。

本轮不改写或执行首次建表 SQL，不生成未经现库核对的迁移脚本。既有 `订单表建表.sql` 是旧基线，尚不含上述增量，不能作为本次完整建表结果。

## 8. 后续验收场景

以下是实施验收要求，本轮未执行：

| 场景 | 预期结果 |
| --- | --- |
| 只打开小票 | 不创建订单 |
| 点击模拟支付 | 创建状态 0 订单，返回固定期限后才可确认 |
| 创建中重复点击 | 当前页面只发一个创建请求，不生成或发送 UUID/Idempotency-Key |
| 创建超时、断网、丢失或畸形成功响应 | 提示结果未知，不重发、不假装失败或成功，可刷新购物车并查看订单 |
| 购物车清理延迟 | 商品仍在也不推断未下单，先查订单，不触发补发创建 |
| 暂不支付、关闭小票、刷新 | 订单仍可查，期限内可继续支付 |
| 创建金额与小票旧价不同 | 按后端成交金额确认，不接受前端旧价覆盖 |
| 合法 0 元支付 | 状态 1、实付 0、有付款时间，不混同未付款 |
| 截止前与恰好到期 | 前者满足条件可支付，后者拒绝 |
| 支付和取消并发 | 只有一个迁移提交成功，不同时形成已支付与已取消事实 |
| 重复支付、重复消息、扫描竞争 | 幂等，不重复记录付款或回补资源 |
| 消息提前、晚到、消费者停机恢复 | 提前不取消，到期不可支付，恢复后最终关单 |
| 第 16 分钟尚未消费消息 | 列表详情仍可见，显示关闭处理中，canPay=false |
| 创建提交后消息发送失败或进程崩溃 | 投递可恢复或由扫描关单，不形成永久待付款孤单；不通过重做整笔下单恢复消息 |
| 下单扣库存与取消回补 | 多商品失败共同回滚，支付不重复扣，取消及消息重复不多加库存 |
| 本地失败或全局回滚 | 不返回虚假成功，不对已回滚下单事实投递有效事件 |
| 跨用户访问、换账号、迟到响应 | 不越权读取或支付，旧结果不覆盖新会话 |
| 历史数据迁移 | 截止时间对应实际创建时间，过期不可支付并最终关单 |
