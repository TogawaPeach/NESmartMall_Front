# 登录服务与网关需求

更新时间：2026-10-14\
需求编号：004\
文档状态：前端用户登录与令牌传递已实现并联调；商家后台、服务发现及后端完整鉴权验收仍待推进。本次未部署服务或执行数据库迁移。

本次账户、昵称、角色、商家标识及完整请求响应统一见 [账户与登录最终约定.md](./账户与登录最终约定.md)。原独立商家绑定、多角色响应与各服务强制验签草案已被本次选择替代。

**当前选择为只解码 JWT、读取身份与角色，不验证签名。该方案无法证明身份真实性，角色和账户 ID 均可伪造，不能保证商家只修改自己的商品。** 本文中的入口限制和归属过滤仅描述功能规则，不宣称安全鉴权已经成立。

## 2. 服务职责与请求入口

| 模块 | 职责 |
| --- | --- |
| mall-auth-service | 查询账户，验证密码哈希与状态，从数据库读取角色，签发 JWT，提供账户信息；后续处理刷新、退出与撤销 |
| mall-gateway | 浏览器统一入口、路由、跨域；解析 JWT 并按解码角色执行入口过滤，本版本不验签 |
| mall-product-service | 解析 JWT 并按解码角色和账户 ID 限定商品操作，本版本身份不可信 |
| mall-common | 小型公共类型，不保存账户持久化逻辑或签发私钥 |
| 前端 | 登录、身份恢复、页面导航、请求附加 Bearer JWT 和错误处理 |
| Nacos | 后续服务注册发现，不处理商城密码验证或 JWT 签发 |

登录链路：前端 → 网关 8080 → 认证服务 8081 → 网关 → 前端。商品请求：前端携带 JWT → 网关解析与角色过滤 → 商品服务解析与归属过滤 → 返回 Result。

网关转发原始 Bearer 令牌，不信任额外客户端身份头。前端 `vite.config.ts` 的 `/api` 代理已于 2026-10-14 从商品服务 8082 切换至网关 8080，保留原请求路径、查询参数和 `changeOrigin: true`；修改后重启 Vite 开发服务器；普通用户登录转发已在浏览器验证，商品与商家路由的完整验收仍待执行。认证与商品服务部署为内部服务。限制直接访问服务不能消除伪造 JWT 的风险。

## 3. 账户模型、角色与导航

一个账户只有一个角色，数据库 `role = 0` 为商家、`1` 为普通用户。商家账号的 `account.id` 同时为商家 ID，不单独建 merchant 表、角色关联表或账户 merchant_id 字段。用户昵称字段为 `nickname`，商家昵称就是店铺名；昵称不参与身份和商品归属判定。

商城共用数据库统一使用现有 `nesmartmall_product`，不改名、不迁移商品表、不另建认证数据库；`account` 与 `product` 同库，分别由认证服务和商品服务管理。账户建表先执行 `USE nesmartmall_product;`。

账户字段方案为 id、account、nickname、password_hash、role、status、created_at、updated_at、last_login_at；建议类型、约束及已确认项与建议项的区别见最终约定第 3 节。不增加 UUID，不在账户表保存 JWT。

密码使用 PasswordEncoder 生成哈希并用 matches 验证。商家角色由可信管理流程授予，不接受客户端在普通注册或登录时自选；账号创建与商家授予流程待确认。

当前用户入口登录成功保留原页面，返回的 role 保存为展示信息；按角色导航为后续目标：`1` 进入商城、`0` 进入商家后台；建议路径为 `/` 和 `/merchant/dashboard`。后台未开发时需先建立可用入口，不能把跳转至不存在页面当作验收成功。当前刷新从 sessionStorage 恢复尚未过期的用户状态，不调用 `/api/auth/me`；后台页面守卫待实现。首次登录失败不建立会话；已有会话时重新登录失败保留原会话，显式退出会清理；迟到或取消的登录结果不得重新建立已退出的会话。

## 4. 登录接口与响应

| 方法与路径 | 用途 | 请求条件 |
| --- | --- | --- |
| POST /api/auth/login | 验证账号密码和状态后签发 JWT | 无 JWT 可调用；JSON 仅包含 account、password |
| GET /api/auth/me | 获取当前账户 id、account、nickname、role | 后续方案，当前前端未接入；根据解析的 sub 查询数据库；因未验签，不能证明调用人身份 |

登录成功返回 HTTP 200 和 Result：code 为 200、message 为 OK、data 包含 accessToken、tokenType、expiresIn、user。`accessToken` 不含 Bearer 前缀，`tokenType` 为 Bearer；user 包含字符串 id、account、nickname、数字 role。商家 nickname 即店铺名，不单独返回 merchantId。完整 JSON 示例见最终约定第 4 节。

缺失、空值或类型错误返回 HTTP 400；账号或密码错误统一提示并返回 HTTP 401；禁用账户不得取得新令牌。密码和密码哈希不返回前端。

本次后端响应的 `expiresIn` 为 `86400` 秒；前端按实际返回值计算 expiresAt。会话存入当前标签页 sessionStorage，刷新恢复不重发登录或调用 me，密码不持久化；关闭标签页或前端退出后结束当前本地会话。HTTP 401 或业务 code 401 清理对应当前令牌的会话，不自动续期。服务端刷新、注销、撤销及账户禁用后的生效策略仍待确认，清除浏览器令牌不表示服务端已经撤销。详见 [用户入口与登录状态需求.md](./用户入口与登录状态需求.md)。

## 5. JWT 处理与角色规则

认证服务仍签发带签名的 JWT，本版本网关及商品服务不校验签名。数据库角色 0 映射 JWT roles 为 ["MERCHANT"]，1 映射为 ["CUSTOMER"]；若映射 Spring 权限，分别对应 ROLE_MERCHANT、ROLE_CUSTOMER。当前 Web MVC 网关使用 Servlet 安全体系。

JWT 使用 sub 表示账户 ID，计划包含 roles、iss、aud、iat、exp。商家 ID 使用商家身份下的 sub，不再增加 merchant_id 声明。具体签发算法、密钥、issuer、audience、有效期及必要声明规则待确认。不验签并不表示选用 alg=none，也不能将标准 Resource Server 验签配置描述成本版本实现。

网关与业务服务读取 Bearer JWT、解析载荷、检查必要字段与时间等声明，再按解码角色执行接口规则。正常请求不必逐次远程调用认证服务；即使按 sub 查库，也无法弥补 sub 可被伪造的问题。

| 请求或情况 | 规则 |
| --- | --- |
| POST /api/auth/login | 允许无令牌，验证账号密码 |
| GET /api/auth/me、商品查询 | 要求符合当前解析及字段规则的令牌；首页首次无令牌入口待确认 |
| /api/merchant/** | 解码 roles 包含 MERCHANT，商品操作继续按 sub 限定 merchant_id |
| OPTIONS 预检 | 在 CORS 策略下放行 |
| 缺失、无法解析、缺少必要字段或检查发现过期 | HTTP 401 + Result |
| 解码角色无商家权限 | HTTP 403 + Result |
| 修改载荷或签名后仍能通过解析与声明检查 | 无验签拒绝保证，可能伪造角色或账户 ID |

登录白名单限定方法与路径，不整体放行 /api/auth/**。不信任客户端额外身份头或商品归属参数；但不能因此宣称 JWT 内的角色或账户 ID 可信。账号停用、角色变更和退出后的生效机制仍待设计，不能仅依赖旧载荷。

## 6. Nacos 与网关路由

Nacos 已确定为项目注册中心，目前尚未接入。先使用现有固定地址路由开发登录，后续接入注册发现，集中配置管理再分阶段推进；Nacos 不是登录签发 JWT 的前置条件。Nacos 管理自身的账号权限与商城用户身份分别处理。

| 请求路径 | 目标服务名 | 当前开发端口 |
| --- | --- | --- |
| /api/auth/** | mall-auth-service | 8081 |
| /api/products/** | mall-product-service | 8082 |
| /api/merchant/** | mall-product-service | 8082 |
| 浏览器统一入口 | mall-gateway | 8080 |

认证、商品服务以各自 spring.application.name 注册；网关连接 Nacos 查询实例，计划使用 lb://mall-auth-service 与 lb://mall-product-service，通过 Spring Cloud LoadBalancer 选择可用实例，保留现有 API 路径。仅引入 Nacos 依赖不能视为网关已经按服务名路由。

网关可统一注册到 Nacos 以便管理，但浏览器仍通过已部署的网关地址访问，不直接调用 Nacos。Nacos 提供服务信息，HTTP 业务请求仍由网关发送至目标实例。

开发、测试、生产环境按命名空间等方式隔离，避免跨环境发现服务或加载配置。配置中心后续可管理各服务非敏感运行配置；账号密码、JWT 私钥等通过受保护的凭据方式提供，不写入仓库或公开配置。

依赖版本以当前 Boot 4.0.x、Cloud 2025.1.x 基线核对 Spring Cloud Alibaba 2025.1.x 的适配组合，并核对其 Nacos 客户端与服务端兼容性；具体 Alibaba、Nacos 和部署版本待实施时确认，不直接照搬旧版教程。

找不到可用实例时，网关返回明确的服务不可用错误，建议 HTTP 503 和失败 Result；前端显示请求失败，不误判为登录过期。实例下线后，应按最终约定的发现刷新时效停止选择失效实例。上游连接失败或超时返回统一 HTTP 5xx 和失败 Result，不误判为 401 或空业务成功；具体状态码、超时值与刷新时效待配置确认。环境隔离或内部网络不能补上当前 JWT 不验签带来的身份伪造缺口。

## 7. 商品归属与统一异常

product 后续增加 merchant_id，逻辑关联商家账号的 account.id。创建商品时由后端根据解码 sub 赋值；读取和修改同时限定商品 ID 与 merchant_id。已有商品按真实归属回填，不能随意指定默认商家；本次不提供或执行迁移。详细规则见商家设计与最终约定。

本版本 sub 未验签，攻击者可能冒充其他商家，归属条件不能被描述为可靠的越权防护。

成功、参数失败、令牌处理失败及权限不足均封装为 Result，HTTP 状态分别使用 200、400、401、403。真实身份前提下跨商家资源建议返回 404；具体业务错误码待定。网关无可用实例返回 503，上游连接或超时返回约定的 5xx，不误判为登录过期或空业务成功。

前端当前在匹配会话的 HTTP 401 / 业务 code 401 时清理登录状态，由用户点击入口重新登录；商品请求仍显示现有失败和重试提示。403 专用权限提示属于后续目标；登录请求的 5xx、超时和网络失败在弹窗内提示。不默认自动刷新或循环重试失效令牌。AI SSE 的错误协议仍按其单独文档执行。

## 8. 实施顺序与验收边界

1. 完成账户字段、昵称、账号创建及商家角色授予规则，准备普通与商家测试账户。
2. 使用现有固定地址网关路由开发登录、密码验证、JWT 签发和当前账户接口。
3. 实现本次选择的载荷解析、角色过滤、统一 Result；前端统一请求网关并传递令牌。
4. 后续接入 Nacos 注册发现及服务名路由，集中配置另行推进。
5. 开发商家后台、商品 merchant_id 与归属过滤，按阶段验收。

| 场景 | 预期与边界 |
| --- | --- |
| 无令牌登录 | 正确密码且账号正常时返回 JWT 和数据库账户信息 |
| 错误密码、缺失参数、禁用账号 | 按上述约定拒绝，不取得新 JWT |
| 普通用户与商家 | role 分别为 1、0；JWT roles 分别为 CUSTOMER、MERCHANT；商家昵称作为店铺名 |
| 只修改响应中的 user.role | 可以误导页面展示，不能直接改变原 JWT 的 roles；但本版本允许 JWT 载荷另被伪造 |
| 按原始普通用户令牌请求商家接口 | 解码角色不足时返回 403 |
| 令牌缺失、不可解析或字段检查失败 | 返回 401，不进入受保护业务 |
| 修改 JWT 的角色、账户 ID 或签名 | 记录当前缺口；本版本无法保证拒绝，不能列为抗伪造通过项 |
| 按原始商家 A 令牌换商品 ID | 归属过滤不应操作 B 的商品；不能据此宣称能防伪造 B 身份 |
| 服务发现 | 后续独立验收注册、负载均衡、实例上下线与错误语义 |
| 用户登录与页面刷新恢复 | 普通用户登录、刷新恢复、退出后刷新及 Esc 关闭已在浏览器验证；8 项 API 与会话测试通过 |
| 商家导航与后台守卫 | 尚未实现，后续单独验收 |

仅上述用户登录、刷新恢复和前端退出已验证；其他后端角色、权限、数据归属与服务发现场景仍待执行验收。身份真实性和可靠商品权限必须与当前功能联调结果区别记录。
