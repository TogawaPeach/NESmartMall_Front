## 1. 已确认需求

1. 用户打开网站首页时，默认选中“全部”选项卡。
2. 首页初始化自动向后端发出一次商品查询请求，无需用户点击选项卡或搜索按钮；若已有尚未过期的本地会话，附加 Bearer JWT。无令牌时当前前端仍发起查询，后端是否公开商品读取尚待确认；用户可点击用户入口登录，登录成功后商品不会自动重查。
3. 后端查询数据库中的商品，默认按销量从高到低排序，返回当前分类范围内排名前八的商品。前端不提供排序选择，也不传 `sort` 参数。
4. “全部”表示跨商品分类查询，不传 `categoryId`；选择全站仪传 1，GNSS / RTK 传 2，水准仪传 3，测距仪传 4，配件传 5。切换分类自动重新查询。
5. 使用 JWT 进行身份鉴权。用户登录后的业务接口请求携带 JWT，后端按当前仅解码约定读取身份与角色；不验签导致身份可伪造。
6. 后端业务接口响应统一封装到 `Result` 结果类中，再序列化为 JSON 返回前端；成功、业务失败和鉴权失败均使用这一封装。
7. 用户登录后，如果账号具有商家身份，切换到商家后台管理。
8. 商家后台支持查看销量、上传商品和下架商品；具体页面、统计口径及接口按需求 002 继续细化。
9. 首页点击“查看全部商品”进入商品列表页，从第 1 页查询，通过翻页浏览当前分类范围内的全部商品；每页固定 12 件，后端使用 PageHelper 分页。
10. 在现有 `ProductController` 中新增分页方法，映射为 `GET /api/products/page`；保留首页 `GET /api/products?limit=8` 的方法和数组响应。分页接口返回本页商品、筛选后的总数、页码和每页数量，详见第 9 节。
11. 登录后由认证服务根据数据库返回角色、昵称和账户 ID，前端据此识别商家并进入后台；商家昵称即店铺名；页面导航、网关入口校验和业务服务授权分别实现。后台页面目前尚未开发，登录服务与网关的阶段范围见第 10 节。
12. 新增表保存商品的商城站内详情页路径，例如 `/products/123`；点击对应商品进入其详情页，新增表归属商品服务，接口与字段草案见第 11 节。
13. 使用 Nacos 注册中心、OpenFeign + Apache HttpClient 5 服务间同步调用与 HTTP 连接池、Seata 跨服务数据库事务；后期使用 RabbitMQ 异步处理下单后的订单展示或通知，并引入 Redis 读取缓存。后续异步处理不并入核心下单的同一分布式事务，适用边界见第 12 节。
14. 后期 AI 导购使用独立 Python 服务，普通调用建议由 Java 通过 HTTP JSON 访问；是否需要流式回答及后台异步任务另行确定，详见第 13 节。

每次首页商品查询的数量上限为 8 条，包括首次打开、刷新页面、切换分类及主动重试。等待请求期间显示 8 张骨架卡片；请求结束后退出骨架屏状态。前端应按后端返回的顺序展示本次查询结果，最多展示 8 件；不足 8 件时展示实际返回数量，不用占位商品补齐。商品列表分页见第 9 节；关键词搜索及其他页面需求另行补充。

## 2. 页面与请求流程

| 步骤 | 前端职责 | 后端职责 |
| --- | --- | --- |
| 首页初始化 | 选中“全部”，搜索词为空，商品区域进入加载状态并显示 8 张骨架卡片 | — |
| 自动查询 | 请求 `/api/products?limit=8`，省略 `sort` 和 `categoryId`；已有有效会话时统一携带 Bearer 令牌 | 接收请求，采用默认销量降序排序 |
| 切换分类 | 发送对应 `categoryId=1～5` 和 `limit=8`；切回“全部”省略分类参数，所有请求省略 `sort` | 先按分类筛选，再默认按销量降序取前八条 |
| 身份处理 | 等待接口结果 | 解析 JWT 并按解码角色过滤，再校验参数并查询；本版本不验签，无法确认身份真实性 |
| 数据查询 | 等待响应，显示 8 张骨架卡片 | 按约定的商品范围与销量口径查询数据库，先筛选分类、再排序，最后取前 8 条 |
| 查询成功 | 解析 Result，按响应顺序渲染商品卡片，取消加载状态 | 返回包含成功状态和商品数组的 Result |
| 无商品 | 显示空列表提示 | 返回业务成功且商品数组为空的 Result |
| 查询失败 | 普通查询失败显示提示和“重试”；鉴权失败按下文规则处理 | 返回对应 HTTP 状态和失败 Result |

同一次首页初始化避免重复发送相同请求。刷新首页重新查询；用户主动重试可以再次发送请求。如果用户在请求完成前切换分类，旧响应不得覆盖当前分类结果。

当前首页无令牌时仍默认选中“全部”并尝试查询，查询是否允许匿名访问由后端策略决定。用户入口已采用登录弹窗，成功后保留当前页面但不会自动重新加载商品；登录后的商品重查时机仍待确认。

## 3. 首页后端查询规则

- 排序方向：后端默认销量降序，销量最高的商品排在第一位；前端不传 `sort`。
- 分类范围：`categoryId` 为可选参数；省略时查询全部分类，传入 1～5 时按对应数据库 `category_id` 筛选。先筛选，再排序并取前八条，不能先取全部分类前八条再在前端过滤。数据库分类 ID 应与本文固定映射一致。
- 数量上限：8 件。必须在全部符合条件的商品中确定前八名，不能先任意取 8 件再排序。
- 商品粒度：每个商品只出现一次；存在多个规格或 SKU 时，销量如何汇总到商品需确认。
- 数据来源：数据库真实数据，不返回演示商品或随机生成的销量。
- 同销量排序：使用商品 ID 升序作为第二排序条件，与现有 SQL 一致；分页查询使用相同顺序。
- 可展示商品范围：仅查询已上架且未删除的商品，即 `status = 1 AND is_deleted = 0`，与现有 SQL 一致；缺货商品是否参加排名仍待确认。
- 销量口径待确认：统计售出件数还是订单数、累计销量还是某个时间段销量，以及订单状态、退款和退货如何计入。前后端必须采用同一口径。

## 4. 首页查询接口约定与鉴权草案

已确认使用 `GET /api/products`，每次传 `limit=8`，不传 `sort`，按需要传可选的 `categoryId`。商品成功响应采用现有接口结构，见 4.2、4.3 节；前端已实现 Bearer 请求头以及 HTTP 401 / 业务 code 401 清理；其他鉴权失败业务码仍待确认。

```http
GET /api/products?limit=8
Authorization: Bearer <JWT令牌>
Accept: application/json
```

| 项目 | 约定 | 说明 |
| --- | --- | --- |
| 方法 | `GET` | 读取商品列表 |
| 路径 | `/api/products` | 已确认；实际服务地址另行配置 |
| `sort` | 不传 | 后端默认按销量降序，前端不提供排序选择 |
| `limit` | `8` | 最多返回 8 件商品 |
| `categoryId` | 可选，1～5 | “全部”省略；其余分类使用下表固定 ID |
| 关键词参数 | 省略 | 首次进入时不附加搜索条件 |
| 鉴权方式 | JWT（已确认） | 本商品查询按携带 JWT 的业务请求编写；后端先鉴权再查询 |
| 令牌传递 | `Authorization: Bearer <JWT>`（已实现） | 登录后通过共享 http 实例自动附加，登录接口不附加旧令牌 |

分类 ID 与请求示例：

| 选项卡 | categoryId | 请求 |
| --- | --- | --- |
| 全部 | 不传 | `/api/products?limit=8` |
| 全站仪 | 1 | `/api/products?categoryId=1&limit=8` |
| GNSS / RTK | 2 | `/api/products?categoryId=2&limit=8` |
| 水准仪 | 3 | `/api/products?categoryId=3&limit=8` |
| 测距仪 | 4 | `/api/products?categoryId=4&limit=8` |
| 配件 | 5 | `/api/products?categoryId=5&limit=8` |

查询参数顺序不影响含义。切换分类后，重试使用当前分类参数。前端已实现上述请求；后端 Controller、Service、Mapper 与 SQL 已接收并筛选 `categoryId`，仍需使用真实数据库联调验收。前端不直接访问数据库。

### 4.1 JWT 处理与角色约定

本次具体约定见 [账户与登录最终约定.md](./账户与登录最终约定.md)，以下为公共接口规则：

- 业务请求统一附加 `Authorization: Bearer <JWT>`；登录 POST /api/auth/login 无令牌可调用，CORS OPTIONS 在跨域策略内放行，不整体公开 /api/auth/**。
- 认证服务查询账户并验证密码哈希与状态后签发 JWT；数据库 role 为 0（商家）或 1（普通用户），分别映射 JWT roles 为 MERCHANT / CUSTOMER。sub 为字符串账户 ID，商家 ID 复用商家账户 ID。
- **用户明确选择后端只解码 JWT、读取角色，不验证签名。** 网关与业务服务可检查必要字段、时间、issuer/audience 等声明，但它们均可伪造，不能确认令牌确由认证服务签发。
- 解码角色用于接口过滤，商品 merchant_id 与解码 sub 用于归属过滤。由于 roles、sub 可篡改，这些功能规则不构成可靠的角色或数据权限保护，不能承诺防止冒充商家及跨商家修改。
- 前端根据登录响应的 user.role 显示页面，user.nickname 用于用户昵称或店铺名。仅修改响应中的 role 不改变原 JWT，但修改 JWT 本身无验签拒绝保障。
- 生产接口使用 HTTPS，本地通过网关 8080 联调。前端 sessionStorage 会话、刷新恢复、本地退出已实现；本次返回 expiresIn 为 86400 秒，前端按实际响应计算过期。服务端刷新、撤销与禁用生效策略仍待确认；无令牌商品访问和登录后商品重查仍待确认，详见需求 007。

| 情况 | 本版本处理 |
| --- | --- |
| 令牌能解析且声明检查、角色规则通过 | 按功能规则执行业务，不能据此认定身份真实 |
| 缺失、无法解析、缺少必要字段或检查发现过期 | HTTP 401 + 失败 Result；按适用情况返回 Bearer 错误头，前端进入重新登录流程 |
| 解码角色权限不足 | HTTP 403 + 失败 Result，前端提示无权限 |
| 篡改角色、sub、签名但仍符合解析规则 | 没有签名校验拒绝保证，可能冒充其他账户 |

不默认自动刷新，不循环重试已发现失效的令牌。恢复签名验证为后续安全修正建议，不能把早期的公钥/JWKS 方案当作本版本已有能力。

### 4.2 统一 Result 结果类

统一使用 `Result<T>` 封装业务接口响应已确认。首页商品接口的 `T` 为商品数组；分页商品接口的 `T` 为包含 `list`、`total`、`pageNum`、`pageSize` 的对象。登录接口的令牌信息也放在 Result 的业务数据字段中，字段与路径见 [账户与登录最终约定.md](./账户与登录最终约定.md)。

商品接口沿用现有 `code`、`message`、`data` 结构，不采用此前的 `code: 0` 与 `data.items` 草案。

| Result 字段 | 类型 | 约定 |
| --- | --- | --- |
| `code` | number | 商品接口以 `200` 表示业务成功；失败码及其他业务接口的状态码待确认 |
| `message` | string | 结果说明，商品成功响应为 `OK` |
| `data` | T / null | 成功时承载业务数据；失败时建议为 `null` |

控制器、鉴权过滤器和统一异常处理层产生的业务接口响应均采用这一结构。前端先处理 HTTP 状态，再检查 `Result.code`，业务成功后才读取 `Result.data`。HTTP 状态码与业务状态码分别约定，不能只因 HTTP 200 就判定业务成功。

后期 AI 导购如启用 SSE，成功响应按约定的事件流传输，不把整条连接包装为单个 Result JSON。流建立前的鉴权及参数失败仍使用 HTTP 状态和 Result，流建立后的失败按事件协议处理，具体扩展见 [AI导购服务通信需求.md](./AI导购服务通信需求.md)。

鉴权失败示例：HTTP 401，响应体如下。`40101` 仅为建议的业务错误码，需后端确认。

```json
{
  "code": 40101,
  "message": "登录状态已失效，请重新登录",
  "data": null
}
```

### 4.3 首页商品查询响应字段

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `code` | number | `200` 表示业务成功 |
| `message` | string | 成功响应为 `OK` |
| `data` | array | 商品数组，最多 8 条，按销量降序、同销量 ID 升序排列 |
| `data[].id` | number | 商品唯一标识，对应现有后端 `Long id`；前端也支持字符串 ID |
| `data[].name` | string | 商品名称 |
| `data[].coverUrl` | string / null | 浏览器可访问的商品封面地址 |
| `data[].price` | integer / null | 人民币价格，以整数分返回；前端除以 100 后展示为元；缺失不能用 0 代替 |
| `data[].sales` | integer | 非负销量，对应数据库 `sales_count`；统计口径仍待确认 |

以下示例假设符合条件的商品只有 1 件，示例商品仅用于说明结构，不作为真实展示数据。

```json
{
  "code": 200,
  "message": "OK",
  "data": [
    {
      "id": 1001,
      "name": "示例商品 A",
      "coverUrl": null,
      "price": 990,
      "sales": 320
    }
  ]
}
```

`price: 990` 表示 990 分，页面显示 `¥9.90`。分页列表复用这些商品字段，不改变金额单位。

无商品时返回 HTTP 200、`code: 200` 以及 `data: []`。参数错误建议返回 HTTP 400，鉴权失败返回 HTTP 401，权限不足返回 HTTP 403，服务或数据库查询错误返回 HTTP 5xx；这些业务接口响应均封装为 Result。具体业务错误码需确认，前端分别处理 HTTP 失败、业务失败和响应格式异常。网络中断或上游服务返回非 Result 响应时，按请求异常处理。

## 5. 首页前端展示与异常处理

本节鉴权状态处理暂按 4.1 节的 HTTP 401 / 403 草案编写，最终按双方确认的状态码执行。

- 加载：首次查询、刷新、切换分类及重试等待响应期间，商品区域显示 8 张骨架卡片。
- 成功：保持后端顺序，不在浏览器中对局部数据重新计算前八名。
- 空列表：只有请求成功、业务成功且商品数组为空时才显示空列表提示。
- 普通失败：网络异常、超时、普通业务失败及响应字段异常均显示失败提示，允许重试；不能误显示为空列表。
- 鉴权失败：HTTP 401 按重新认证流程处理，HTTP 403 显示无权限提示；收到已约定的鉴权业务错误码时同样处理，不用失效令牌循环重试。

## 9. 需求 003：查看全部商品与 PageHelper 分页查询

### 9.1 页面行为

- “查看全部商品”表示通过分页浏览全部符合条件的商品，每次请求只返回一页。
- 首页“全部”选项卡下点击入口，在新标签页打开商品列表页，查询全部分类第 1 页；分类入口（例如“查看全部全站仪”）保留当前分类并查询第 1 页，与现有前端行为一致。
- 点击其他页码时，保留分类并发送新页码；切换分类时从第 1 页重新查询。
- 每页固定 12 件；分页组件使用 `prev, pager, next`，不提供每页条数选择器。页数由后端 `total` 计算，例如 50 件商品共 5 页，最后一页 2 件。
- 等待响应期间显示加载状态；成功展示本页真实商品，失败显示提示并允许按当前分类和页码重试。旧请求的迟到响应不得覆盖最新结果。
- 列表页关键词搜索暂未开放，前端不发送关键词参数。

### 9.2 请求约定

| 项目 | 约定 |
| --- | --- |
| 方法与路径 | `GET /api/products/page` |
| `pageNum` | 从 1 开始；前端每次发送，后端未收到时默认 1；必须是后端页码类型可接受的正整数 |
| `categoryId` | 可选；“全部”不传，全站仪传 1、GNSS / RTK 传 2、水准仪传 3、测距仪传 4、配件传 5 |
| 每页数量 | 后端固定 12，前端不传 `pageSize` |
| 其他参数 | 前端不传 `limit`、`sort` 或关键词；后端默认排序 |
| JWT | 沿用 4.1 节的业务接口鉴权要求，具体接入仍待实现 |

“全部不传分类参数”仅指省略 `categoryId`；分页请求仍发送 `pageNum`，首页请求仍发送 `limit=8`。不以 `categoryId=0` 或 `categoryId=all` 表示全部。

| 场景 | 请求示例 |
| --- | --- |
| 全部商品第 1 页 | `/api/products/page?pageNum=1` |
| 全部商品第 2 页 | `/api/products/page?pageNum=2` |
| 全站仪第 1 页 | `/api/products/page?categoryId=1&pageNum=1` |
| 全站仪第 2 页 | `/api/products/page?categoryId=1&pageNum=2` |

开发环境浏览器请求 `http://localhost:5173/api/products/page?pageNum=1`，由现有 Vite `/api` 代理转发至后端；前端使用相对 API 路径，部署地址不硬编码。

### 9.3 后端分层与查询要求

1. 在现有 `ProductController` 中新增分页方法（建议命名 `pageProducts`），方法映射为 `@GetMapping("/page")`，与类级 `/api/products` 组合形成完整路径。保留原 `listProducts` 方法的路径、参数和数组响应，不新建 Controller。
2. `ProductService` 及其实现新增分页方法。Controller 接收并校验参数、调用 Service、封装 Result；Service 负责设置 PageHelper 页码、固定页大小 12，并启用总数查询。
3. PageHelper 设置后紧接着执行目标 Mapper 查询，中间不得插入其他 MyBatis 查询。由 PageInfo 或 Page 的分页信息取得本页商品和筛选后的总数；返回字段按 9.4 节封装。
4. 分页 Mapper 查询不带手写 `LIMIT`，由 PageHelper 添加数据库分页限制；现有首页查询可继续保留原来的 `LIMIT #{limit}`。不能把首页最多 8 条的结果作为分页数据源，也不能先查询全部数据再在 Java 或前端截取。
5. SQL 使用 `status = 1 AND is_deleted = 0`；仅在传入 `categoryId` 时追加对应筛选条件。“全部”省略分类条件，不排除未分类且满足展示条件的商品。
6. 先筛选，再按 `sales_count DESC, id ASC` 排序、分页；总数统计使用相同筛选条件。每个商品在同一页只出现一次。
7. 设置 `reasonable=false`，禁止 PageHelper 自动把越界页码改为末页。请求超过最后一页时，返回原请求 `pageNum`、实际 `total`、`pageSize: 12` 和 `list: []`；前端计算最后一页、更新页面 URL 后重新查询。无商品时最后一个可显示页码按 1 处理。
8. 非正整数、无法解析或超出后端页码类型范围的 `pageNum` 按参数错误处理，不执行分页商品查询；具体失败业务码沿用统一错误约定。

PageHelper 的生效位置与 `reasonable` 参数说明参考 [官方使用文档](https://github.com/pagehelper-org/Mybatis-PageHelper/blob/master/wikis/zh/HowToUse.md) 和 [重要提示](https://github.com/pagehelper-org/Mybatis-PageHelper/blob/master/wikis/zh/Important.md)。

### 9.4 分页响应

成功响应为 HTTP 200，响应体 `code: 200`。`data` 包含以下字段；商品条目复用 4.3 节的 `id`、`name`、`coverUrl`、`price`、`sales`。

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `data.list` | array | 本页商品，最多 12 件；无商品或越界页时为空数组 |
| `data.total` | integer | 当前筛选范围内的商品总数，非负，不是本页数量 |
| `data.pageNum` | integer | 与请求页码一致；未传时为 1，包括空结果和越界页场景 |
| `data.pageSize` | integer | 固定返回 12，即使本页不足 12 件 |

示例：符合条件的商品只有 1 件，返回第 1 页。

```json
{
  "code": 200,
  "message": "OK",
  "data": {
    "list": [
      {
        "id": 1001,
        "name": "示例商品 A",
        "coverUrl": null,
        "price": 990,
        "sales": 320
      }
    ],
    "total": 1,
    "pageNum": 1,
    "pageSize": 12
  }
}
```

前端验证分页字段、商品字段和业务状态；字段异常时显示失败提示，不把异常结果当作空列表。`total` 与数值页码须在前端安全整数范围内。

- Nacos 负责注册发现；OpenFeign 调用服务，Apache HttpClient 5（HC5）复用 HTTP 连接池；网关转发仍使用 Gateway 的路由与客户端机制。
- 当前 OpenFeign 5.x 已移除 OkHttp 自动配置，本项目默认改用内置支持的 HC5；实施时仍需验证服务发现、负载均衡、连接复用与超时。
- Seata 用于需要共同提交或回滚的跨服务数据库写入，具体事务模式与业务范围待明确；同服务同数据源的多表操作使用本地事务。
- 后期 RabbitMQ 处理下单成功后的独立订单展示更新或通知；订单事实先持久化，异步消费者不成为原下单事务分支。可靠投递、幂等、重试及全局事务成功后发布的要求同步设计。
- 后期 Redis 缓存商品等业务读取；缓存范围与 TTL 待细化，写入后失效、并发旧值修复、权限隔离和故障回源保护纳入验收。

订单列表如直接查询订单表，仅为读接口；如采用独立展示表，通过消息更新并明确展示延迟。具体订单服务、订单模型和列表投影尚未设计，本节不新增已实现的订单功能。

已确认：后期 AI 导购作为独立 Python 服务部署。当前前端入口暂未开放，后端与 Python AI 服务尚未实现。

通信与职责方案见 [AI导购服务通信需求.md](./AI导购服务通信需求.md)：普通推荐用 OpenFeign + HC5 调 HTTP JSON；逐段回答如启用则使用独立 SSE 流式协议；后台长任务如启用则使用 RabbitMQ。Python 注册发现纳入 Nacos，Java 负责权威业务数据与权限，Python 负责 AI 推理，模型调用不启动 Seata 全局事务。

Java 编排入口归属、Python 框架、模型供应方、是否首期流式、会话存储、内部身份与超时等仍属实施建议和待确认事项。

## 14. 需求 007：用户入口与登录状态

2026-10-14 已实现商城顶部用户入口登录弹窗，提交 POST `/api/auth/login` 的 JSON 账号密码，成功后留在当前页面、显示昵称菜单并支持退出。登录会话使用当前标签页 sessionStorage，刷新时恢复尚未过期的 token 和用户展示信息；后续接口用 `Authorization: Bearer <accessToken>` 传递身份，不重发账号密码或整个用户对象。前端到期及匹配当前令牌的 HTTP 401 / 业务 code 401 清理会话，不自动续期。
