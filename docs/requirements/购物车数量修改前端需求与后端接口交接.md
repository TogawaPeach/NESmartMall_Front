# 购物车数量修改前端需求与后端接口交接

更新时间：2026-10-17

最新后端状态：2026-10-17 已接齐 PUT 数量修改及独立 DELETE 删除代码，未运行编译、测试或真实联调。用户最终确认 quantity 必须大于 0，0 不执行删除；修改数量不检查库存，库存留到支付时验证。详见 本地 Require 中的《购物车数量修改与删除后端实现交接.md》。

最新标识约定：用户明确在 PUT 路径传商品 productId；后端按可信当前用户与 product_id 定位购物车记录。

同日防抖最终约定：每个商品独立计时，最后一次调整数量后 0.8 秒只提交最终值；不展示等待/保存过程文案，仅在失败时提示。此更新只改前端调度和提示，不改变 PUT 最终数量契约。

当前状态：前端与显式开发模拟已实现，真实后端 PUT 代码也已接齐，尚待用户联调。GET 购物车查询此前已由用户确认联调正常；商品详情页原有 POST 加入购物车保持原契约。

## 1. 本轮最终决定

购物车使用 Element Plus 的 ElInputNumber，支持加号、减号及直接输入多件数量。新开一个接口，将条目数量设置为用户修改后的最终值；不采用增量 1/-1，不扩展原有 POST 接口，也不把加入购物车改成 PUT。

| 场景 | 请求 | quantity 含义 |
| --- | --- | --- |
| 商品详情页加入购物车 | POST /api/cart，body 含 productId 和 quantity: 1 | 本次加入件数，已有商品累加 |
| 购物车增减或直接输入 | PUT /api/cart/{productId}/quantity，body 仅含 quantity | 修改后的最终件数，替换原数量 |

例如原来 2 件，用户输入 6，提交 quantity: 6，最终为 6 件；同一 PUT 重复提交仍为 6 件。数量修改请求在路径传商品 productId，以字符串保留大整数精度；页面的勾选、草稿、计时器与保存状态仍按 cartItemId 管理，不把两种 ID 混用。

## 2. 新接口约定（后端代码已接齐，待联调）

```http
PUT /api/cart/123/quantity
Authorization: Bearer <token>
Content-Type: application/json

{"quantity":6}
```

- 路径 productId 为商品 ID 的正整数字符串；body 只发送 quantity，不重复发送 productId，也不传 cartItemId、userId、价格、库存或内部身份头。
- quantity 是最终数量，必须为正整数；1 表示保留一件，不表示增加一件。不能传 0、负数、小数或字符串数量。
- 当前数据库 quantity 为 INT，前端最高支持 2147483647，这是字段类型范围，不是新设的业务购买上限；实际可输入上限还受库存约束。
- 成功要求 HTTP 成功且业务 code 为数字 200；前端不依赖成功 data，推荐响应如下：

```json
{"code":200,"message":"购物车数量修改成功","data":null}
```

后端实现要求：

1. 复用 gateway 登录校验和 cart 当前用户上下文。按 product_id 和可信 user_id 定位已有购物车记录，沿用同用户同商品唯一约束，不能只按商品 ID 更新，也不能接受前端自报用户 ID。
2. 只修改已有条目，不新增商品，不把 PUT 当成累加，也不在数量为 0 时删除。
3. 按用户最新决定，修改数量不查询商品服务、不检查库存或在售状态；库存留到支付时验证，本轮尚未实现支付校验。quantity 用 Integer 接收，受 INT 类型范围限制，不扣减或预占库存。前端现有库存输入限制保持原样，本轮未修改。
4. 保存指定最终值，保留条目 ID、用户及商品引用。重复设置相同值应成功，不能单凭 UPDATE 返回 0 就判定条目不存在。
5. 当前实现对非法参数、当前用户购物车不存在该商品均通过 IllegalArgumentException 返回 HTTP 400；并未新增 404 映射。服务异常沿用 500，JSON 沿用 code/message/data。401 仍交给现有网关及前端统一会话机制处理。
6. 当前不接 Redis、MQ、Seata 或额外内部来源凭据；未新增锁或事务注解，运行及并发行为仍待用户验收。前端库存限制不替代未来支付时的库存校验。

前端已对接上述路径。后端已新增 UpdateCartQuantityDTO、Controller PUT 方法、Service 方法及按当前用户与商品 ID 限定的 Mapper 更新；按用户要求未运行编译或测试。

## 3. 前端交互与异常

- 常规可购买条目展示数字输入框：最小值 1、步长 1、精度 0，上限为当前库存与 INT 范围的较小者，不写死为示例中的 10。
- 用户按加减按钮，或直接键入有效数量（组件 input 事件，无需先失焦）后，启动该商品独立的 800ms 防抖计时；期间再次修改取消旧计时并重新等待，只提交最后一次最终数量，不按每个输入字符立即发请求。输入中的空值、非整数会取消旧提交；清空后恢复当前已确认数量，不提交空值或 0。组件 change 事件仍归整完成编辑时的数值，超范围输入限制在有效范围，API 层独立校验正整数与字段范围。
- 等待期间输入框保持可编辑并显示草稿数量，不展示等待保存提示；如果改回当前已确认数量，取消待发送请求，不发送无变化的 PUT。不同商品独立计时，互不重置。
- 缺货、下架、失效、库存未知或价格未知的条目保留原数量展示，不提供可提交的数量输入框。
- 已有数量超过库存时不在加载时静默改数据，保留原数量和库存不足提示；用户主动减量或输入后限制到有效库存上限。例如原 12 件、库存 8 件，点减号后提交最终 8 件。
- 每个条目独立保存。仅实际发送请求期间禁用该条目的输入框，防止重复提交，不展示保存过程提示；其他条目可独立操作。等待防抖及实际保存期间均禁用“刷新购物车”，避免列表刷新与待保存草稿或未完成写请求竞争。
- 保存成功后更新页面内已确认的数量，自动重算小计、所选件数及参考合计，保留现有勾选。金额只按已确认数量计算，不提前显示保存成功；不额外自动查询 GET。
- 明确失败保留原数量，输入框恢复原值，在条目旁显示后端 message 或通用错误，不自动重试。断网/超时可能已经落库，提示检查网络并刷新购物车确认，不能承诺服务端已回滚。
- 匹配当前会话的 401 继续由统一拦截器清会话，购物车显示登录引导；403/业务错误不主动退出。退出、过期、切账号或卸载时清除待发送计时器、取消未完成请求并清空旧状态；计时结束发送前再次核验身份和页面版本，旧账号草稿不带新账号令牌提交，迟到响应不覆盖新账号。离开页面不额外强制提交待发送草稿。
- 手动刷新仍沿用原行为清空勾选；保存数量成功不清空勾选。每行删除按钮现已接入 ElPopconfirm 确认和 DELETE /api/cart/{productId}，成功后移除、失败保留；后端删除代码已接齐、待用户联调，创建订单、提交购买未开放。删除请求及失败处理见 [购物车删除按钮前端需求与实现交接](./购物车删除按钮前端需求与实现交接.md)。
