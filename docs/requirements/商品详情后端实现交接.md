## 1. 本阶段目标与范围

仅实现 GET /api/products/{id}，经现有 gateway 转发至 mall-product-service。前端在新标签页打开 /products/{id} 后直接读取商品详情，刷新和直接访问使用相同流程。

取消此前 GET /api/products/{id}/detail-entry 的实现要求；不再返回 productId/detailPath，不查询或新建 product_detail_page 路径关联表，不使用 DETAIL_NOT_CONFIGURED。此前给出的入口 VO、Controller、Service 示例不再作为实施目标；若已手写，后端开发者应清理相关入口代码。

前端项目为 /Users/lightfull/NESmartChoice_Before/NESmartMall，已调整 src/api/productDetail.ts 及相关测试和文档，直接请求详情内容，取消入口专用校验和状态。完整要求见 [商品详情页需求.md](./商品详情页需求.md)。

本阶段不包含订单、购物车写入、库存扣减/回补、SKU、图片下载上传或商户后台。每个商品只有一个型号，model 为普通展示字段。

## 2. 必须实现的接口

### 2.1 查询商品详情内容

```http
GET /api/products/123
Authorization: Bearer <accessToken>
```

成功响应：

```json
{
  "code": 200,
  "message": "OK",
  "data": {
    "id": "123",
    "name": "全站仪",
    "model": "NTS-332R",
    "coverUrl": "https://example.com/product-cover.jpg",
    "price": 990000,
    "sales": 36,
    "stock": 20,
    "detailImages": [
      "https://example.com/detail-1.jpg",
      "https://example.com/detail-2.jpg"
    ]
  }
}
```

| 返回字段 | 商品数据库来源 | 对接要求 |
| --- | --- | --- |
| id | product.id | 返回 string，与请求 ID 一致，避免 BIGINT 精度丢失 |
| name | product.name | 非空 string |
| model | product.model | 单个 string 或 null；不返回数组，不建立型号选择器 |
| coverUrl | product.cover_image_url | 完整 HTTP/HTTPS 图片链接或显式 null；不要直接返回数据库列名 |
| price | product.price | 非负整数分或显式 null；示例 990000 显示 ¥9,900.00；0 是有效价格 |
| sales | product.sales_count | 非负整数，返回字段名称为 sales |
| stock | product.stock | 非负整数，0 是有效缺货值 |
| detailImages | product.detail_image_urls | 真实 string[]，无图返回 []，不能返回 null 或字符串形式的 JSON |

price、sales、stock 的 JSON number 必须处于 JavaScript 安全整数范围（0～9007199254740991）。不在该范围时按统一数据异常处理，不能默默截断或擅自改为前端不支持的字符串；若以后扩大金额范围，先同步契约。model 缺失或 null 时前端隐藏型号行。coverUrl 和 price 缺值时仍应保留键并返回 null，当前适配器不接受省略这两个字段。

数据库 JSON 按项目现有持久层技术解析为 List<String> 后交由统一 JSON 序列化返回，保留原有顺序，不去重、不排序；逐项校验完整 HTTP/HTTPS 链接。平台只保存、返回链接，不由后端下载外部图片。详情接口不返回整个数据库实体或额外身份字段。


商品查询保留 status = 1 且 is_deleted = 0 条件，查不到统一返回“商品不存在”；没有详情图片不影响商品存在性，正常返回 detailImages: []。不再增加入口关联或路径一致性检查。

## 3. 错误响应与鉴权

沿用 Result 的 code/message/data，code 为数字，成功 HTTP 200、code 200。失败沿用统一异常处理，建议 HTTP 状态与业务码一致；前端处理 HTTP 200 内的非 200 业务码，HTTP 失败状态优先。

| 情况 | HTTP / code | 响应与前端行为 |
| --- | --- | --- |
| 未登录、令牌无效或过期 | 401 / 401 | gateway 拦截；前端登录成功后重新读取 |
| 无访问权限 | 403 / 403 | 显示无权限，不误报 401 |
| 商品不存在、下架或删除 | 404 / 404 | message 为“商品不存在”，data 为 null；前端显示商品不可访问 |
| 非法 ID | 400 / 400 | 使用框架参数绑定和统一异常处理，无需在 Service 堆叠重复格式校验 |
| 数据格式异常、数据库或服务故障 | 500 / 500 | 显示失败并允许重试，不冒充商品不存在 |

无商品示例：

```json
{
  "code": 404,
  "message": "商品不存在",
  "data": null
}
```

无图片不是错误：商品正常返回 200，detailImages 为 []，不返回“详情未配置”。

gateway 继续负责登录和 JWT 校验，商品服务不复制 JWT 校验器，不新增公开白名单，不公开整个 /api/products/**。不得将 token 或用户身份参数拼入页面或图片 URL。

现有 GET /api/products、GET /api/products/page、分类及关键词分页保持可用；/page 不能被当成 ID。复用现有 gateway 到商品服务的路由和端口，开发调用通过 8080 网关。

## 4. 实现步骤与数据库边界

1. 用户手写后端，按 Controller → Service → Mapper 分步完成；本聊天提供代码与说明，不直接编辑后端代码。
2. 新增详情响应 ProductDetailVO；GET 无请求体，不要求新增请求 DTO。Controller 调用详情 Service，使用 Result 包装响应。
3. Mapper 按 ID 从 product 查询可展示商品，映射 model、cover_image_url、price、sales_count、stock、detail_image_urls。不关联详情路径表。
4. Service 处理查询结果：查不到统一“商品不存在”，查到返回内容，详情图片解析为 List<String> 并保持顺序，无图为 []。复用统一异常处理，不重复校验登录或详情入口。
5. 按用户要求，本阶段不执行建表、加列、删表、回填或库存更新。商品字段既有约定见 [商品表设计.md](./商品表设计.md)；如实际缺列，记录问题并另行讨论，不自行迁移。
6. 前端已移除入口请求及专用状态；后端进行对应验证后，经 gateway 使用真实数据联调，并记录实际完成情况。本轮前端测试不证明后端已实现或部署。

## 5. 验收清单

- 有效登录访问已上架且未删除商品，GET /api/products/{id} 返回全部约定字段。
- 初次加载、刷新或直接访问只请求详情内容，不请求 detail-entry。
- id 使用 string，价格为整数分；零价、null 价格、零销量、零库存正常处理。
- model 为单个 string 或 null，coverUrl 缺失返回 null，无详情图返回 []。
- 图片数组是真实 JSON 数组，保持原顺序，不返回二次编码字符串。
- 无 token/失效 token 由 gateway 返回 401；403 不误报 401；商品服务不重复验 JWT。
- 不存在、下架、删除商品统一返回“商品不存在”；不要求路径关联记录。
- 非法参数按统一机制处理，数据库或服务故障不伪装成无商品。
- 首页、分类、分页及关键词搜索无回归，列表不附加详情图片数组。
- 单次请求改造测试、构建和真实数据联调分别记录；旧版前端 109 项通过不代表新版本通过。
- 本次未修改数据库；前后端实际实现状态与验收结果须据实更新。
