# 微服务基础设施与通信需求

更新时间：2026-10-14\
文档状态：技术选型已记录，尚未接入；本次只修改需求文档，不修改应用代码、部署中间件或执行数据库迁移。

本文补充 [需求.md](./需求.md) 和 [登录服务与网关需求.md](./登录服务与网关需求.md)，记录服务发现、同步调用、分布式事务、后期消息队列与缓存的建设约定。商品详情入口见 [商品详情页需求.md](./商品详情页需求.md)。

后期独立 Python AI 导购服务的通信建议见 [AI导购服务通信需求.md](./AI导购服务通信需求.md)。普通推荐采用已有 HTTP 调用方案；流式回答与异步任务按各自协议设计，不假定普通 Feign JSON 调用已覆盖 SSE。

## 1. 已确定的技术选型与阶段

| 技术 | 用途 | 建设范围 |
| --- | --- | --- |
| Nacos | 服务注册中心，注册与发现服务实例 | 登录先用现有固定地址网关路由，注册发现后续接入；配置中心再分阶段推进 |
| Spring Cloud OpenFeign | 服务之间的同步 HTTP 调用 | 在实际存在跨服务调用时接入，不用于替代浏览器请求或网关路由 |
| Apache HttpClient 5（HC5） | OpenFeign 底层 HTTP 客户端，复用 HTTP 连接池 | 默认采用当前 OpenFeign 内置支持的 HC5 集成 |
| Seata | 需要共同提交或回滚的跨服务数据库事务 | 项目分布式事务工具已确定；具体业务范围和模式随跨服务写入需求确定 |
| RabbitMQ | 异步业务事件、通知与独立展示数据更新 | 后期接入；下单成功后的订单展示更新或通知不并入下单的同一分布式事务 |
| Redis | 业务读取缓存 | 后期接入；缓存对象、时效及失效策略随接口明确 |

当前技术基线为 Java 21、Spring Boot 4.0.8、Spring Cloud 2025.1.3。选定组件不表示全部已经接入，也不表示每个请求必须使用全部组件。中间件的具体版本、部署、容量和运行参数在实施前核对。

## 2. 服务发现、同步调用与 HTTP 连接复用

### 2.1 Nacos 注册中心

认证、商品及后续业务服务以稳定服务名注册到 Nacos；调用方按服务名发现可用实例，通过 Spring Cloud LoadBalancer 选择实例。网关仍采用 Gateway 的服务名路由，浏览器统一访问网关。

环境隔离、实例下线、无可用实例、错误响应及网关路由要求沿用 [登录服务与网关需求.md](./登录服务与网关需求.md)。不得在业务代码固定某一实例地址，也不得让浏览器查询注册中心。

### 2.2 OpenFeign 与 Apache HttpClient 5

服务间需要同步获得结果时使用 OpenFeign；同一个服务内部的 Service 或 Mapper 调用不经过 Feign。服务调用保留自身的超时和失败语义，不将调用失败伪装为空业务成功。

底层 HTTP 客户端采用 Apache HttpClient 5（HC5），复用长期存在的客户端与 HTTP 连接池，不为每个业务请求新建客户端。需要明确连接池总上限、各目标连接上限、获取连接等待超时、连接与读取超时、空闲连接清理及客户端关闭规则；具体数值按调用目标和负载确定。

当前 Spring Cloud OpenFeign 5.x 已移除内置 OkHttp 自动配置。OkHttp 仍可通过原生 Feign 适配器和自定义 Client 接入，但本项目默认使用当前版本内置支持的 Apache HttpClient 5，减少自定义适配。实施时通过受管理的兼容依赖启用 HC5，并验证实际客户端与连接池生效。[OpenFeign 官方客户端说明](https://docs.spring.io/spring-cloud-openfeign/reference/spring-cloud-openfeign.html)、[OkHttp 自动配置移除记录](https://github.com/spring-cloud/spring-cloud-openfeign/pull/1258)

使用 HC5 时保留 Spring Cloud LoadBalancer 集成，需要确认请求实际使用 HC5，也能按 Nacos 服务名发现和选择实例；引入 HTTP 客户端依赖不能单独视为服务发现已经完成。

HC5 此处用于 Feign 同步调用；网关 Web MVC 自身的 HTTP 转发客户端单独按 Gateway 的支持方式配置，不能认为添加 Feign 的 HC5 配置后网关转发也自动使用相同连接池。

服务间调用的身份传递另行明确：代表用户的调用传递适用身份，服务自主调用采用约定服务身份；下游继续执行权限规则，不信任额外客户端身份头。当前 JWT 仅解码、不验签，用户身份可伪造，不能称为已验证身份；缺口见 [账户与登录最终约定.md](./账户与登录最终约定.md)。涉及 Seata 的调用还需要传播事务上下文，事务 ID 不替代用户身份。

写入调用的重试必须与业务幂等规则一起设计。创建订单、扣减库存等操作不能在没有幂等约束时自动重复执行；连接失败或超时也不能简单断言上游一定未完成写入。

## 3. 本地事务与 Seata 的边界

| 场景 | 事务约定 |
| --- | --- |
| 用户点击商品，读取详情页路径或商品内容 | 读取流程，不启动分布式事务 |
| 商品服务在同一数据源修改商品主表和详情路径表 | 商品服务本地事务 |
| 一项业务需要多个服务、多个数据源的写入共同成功或回滚 | 使用 Seata，实施前明确参与者与事务模式 |
| 下单成功后更新独立订单展示数据、发送通知 | RabbitMQ 异步处理，不作为原下单事务的分支 |
| 更新或失效 Redis 读取缓存 | 缓存一致性策略，不把 Redis 缓存操作直接当作 Seata 数据库事务分支 |

Seata 已选为项目的分布式事务工具，但新增第二张表不自动构成分布式事务。商品主表与详情路径表由商品服务统一管理，不为使用 Seata 人为拆成两个服务。

未来下单是否涉及订单、库存等多个服务，及哪些写入必须共同成功，尚需在订单需求中明确。订单、库存、支付服务当前未建立，本文不宣称完整下单事务方案已经确定，也不将支付等外部系统任意纳入 Seata AT 回滚范围。

Seata 模式、客户端与服务端版本、事务组、协调器注册、数据源支持和失败处理在实施前确定。若采用 AT 模式，需要核对代理数据源、参与库的 undo_log、支持的 SQL 与主键、全局锁、事务上下文传播，以及提交或回滚失败后的恢复流程。[Seata AT 官方文档](https://seata.apache.org/docs/user/mode/at/)

只有已经定义参与范围的跨服务写入流程使用全局事务；网关转发、JWT 载荷解析（本次选择不验签）和读取商品路径不因此启动全局事务。

## 4. 后期 RabbitMQ：下单后的异步事件

### 4.1 业务语义

已明确后期加入 RabbitMQ，使用消息通知解耦下单成功后的后续处理。订单服务首先持久化权威订单事实；独立订单列表展示数据或通知消费者通过消息更新，消费者失败不回滚已成功的下单。

如果订单列表直接查询订单服务的订单表，它属于读接口，不需要另一个事务，也不必为了展示列表创建消息消费者。若采用独立的订单列表投影或展示表，则通过 RabbitMQ 更新，允许约定范围内的展示延迟。订单事实不能只靠通知消费者创建，否则消费者故障会导致成功下单没有订单记录。

事件建议暂名 OrderCreated；“下单成功”不等同于“支付成功”，支付成功以后使用独立事件和状态。事件的准确业务触发点、订单状态、展示更新目标服务及延迟要求随订单需求定案。

RabbitMQ 面向后端消费者。浏览器获取订单列表仍通过网关访问 HTTP 接口；页面是否需要自动推送、轮询或手动刷新另行确定。

### 4.2 可靠发布与消费

建议采用事务消息表（Outbox）保证订单事实和待投递事件不会出现数据库与消息直接双写的空隙。以订单服务本地事务为例：

1. 在同一数据库事务保存订单及待投递事件，任一写入失败则一起回滚。
2. 事务提交后，由可靠投递任务读取事件并发布到 RabbitMQ。服务在提交后崩溃或 RabbitMQ 暂时不可用时，待投递记录仍能恢复处理。
3. 使用发布确认并处理消息未路由到目标队列的情况；确认 broker 接收不代表消费者已经处理完成。
4. 消费者在本地事务中更新展示数据或完成持久化处理，并按事件 ID 或业务唯一约束保证幂等；处理成功提交后再确认消息。
5. 发布确认丢失、重复投递或消费后确认丢失都可能造成重复，不能承诺天然恰好一次。失败采用有上限的重试与死信或人工处理，避免无限立即重入队列。[RabbitMQ 可靠性说明](https://www.rabbitmq.com/docs/reliability)

RabbitMQ 的队列、交换机与绑定需明确持久化要求，关键事件使用持久化消息；可靠性与可用性还需结合队列类型、部署和重试设计，不只靠一个配置开关。

建议事件至少包含 eventId、eventType、schemaVersion、orderId、occurredAt 和适用的业务版本；具体内容随消费者所需字段确定，不携带密码、私钥或用于长期消费的用户 JWT。多消费者各用独立队列，不把通知和订单列表投影放在同一竞争队列而导致只能处理其中一个。

后续订单状态事件可能重复或乱序，消费者应按业务版本和状态转换规则处理，避免较旧事件覆盖较新状态。

### 4.3 与 Seata 的关系

RabbitMQ 消费者在自己的事务中执行，不沿用原下单事务的 XID，也不等待订单展示和通知完成后才认定核心下单成功。

若未来核心下单使用 Seata，全局事务最终成功后才能发布对应成功事件。AT 分支本地提交不等于全局提交完成，不能直接让普通 Outbox 扫描在第一阶段就发送成功消息；实施时必须补充全局提交确认、发布资格和失败恢复方案。全局回滚不能留下可对外投递的成功事件。

## 5. 后期 Redis：读取缓存

已明确后期加入 Redis 做缓存。MySQL 仍为账号、商品和订单事实的权威数据源；Redis 读取缓存不承担永久保存订单事实的职责。具体缓存对象与 TTL 尚未逐项确认。

| 候选缓存 | 需要包含或考虑的维度 |
| --- | --- |
| 首页销量前八与分类查询 | 分类、展示范围、销量排序、数量上限及返回结构 |
| 商品分页 | 分类、页码、固定页大小、排序及总数 |
| 商品详情入口和内容 | 商品 ID、有效路径、商品状态与数据版本 |
| 商户后台数据，如后续确有缓存需求 | 可信商户范围与权限，禁止共用缓存泄漏他人数据 |

拟采用 Cache-Aside：先读缓存，未命中查询数据库并写入带有效期的缓存；业务修改提交后主动失效相关缓存。TTL 与主动失效结合，不能只等待过期处理商品下架、路径修改或销量变化。[Redis Cache-Aside 官方说明](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

商品上下架、删除、分类、价格、详情路径和销量变更，需要列出受影响的单商品、首页与分页缓存；失效失败须有重试或修复机制。并发回源可能在更新后填回旧值，实施时明确采用版本、协调回源或可恢复失效等方案，以及允许的过期数据窗口。缓存不能绕过最终商品可访问状态和商户权限检查。

缓存键包含完整查询与授权范围；无商品的短期缓存、热点回源保护、TTL 分散和容量淘汰按实际负载设计，不能以空缓存代替数据库错误或为失败响应填充演示数据。

Redis 暂时不可用时，非关键读取缓存可按限流与并发保护策略回源数据库；应避免缓存故障把数据库压垮。Redis 与数据库都不可用时返回明确失败，不伪装为空业务成功。

未来如通过 RabbitMQ 事件异步失效缓存，消费者仍需幂等和失败恢复，且明确延迟上限。采用 Seata 的写入流程，其缓存失效与发布应围绕最终事务结果安排，不能将分支第一阶段提交当作最终数据变更完成。

基于 AT 第一阶段本地提交、第二阶段可能回滚的时序，并发缓存未命中请求可能读到尚未全局定案的数据。实施时需明确读取隔离或缓存回填修复方案，全局回滚后不得长期保留暂态缓存，提交、回滚与崩溃恢复都要验证；这一缓存要求由 Seata 的事务隔离机制推导，具体实现另行设计。[Seata 事务隔离说明](https://seata.apache.org/docs/user/appendix/isolation/)

Redis 是否还用于刷新令牌、撤销状态、幂等记录或分布式锁，本次没有确认。此类状态应独立定义持久性、TTL 和故障语义，不能与可随时丢弃的业务读取缓存混为一类。

## 6. 建设顺序与验收

当前先用固定地址网关路由推进登录，后续接入 Nacos 注册发现；需要真实同步调用时接入 OpenFeign + Apache HttpClient 5，验证版本、连接池和负载均衡。商品详情路径在商品服务内建设；Seata 在明确的跨服务写入流程落地。RabbitMQ、订单异步处理与 Redis 缓存为后期建设，按对应业务验收。

| 验收点 | 预期结果 |
| --- | --- |
| 注册发现 | 服务名注册，调用方按可用实例路由，环境隔离，无实例错误明确 |
| OpenFeign + HC5 | 确认实际客户端为 Apache HttpClient 5，连接复用、池容量与超时生效，Nacos 服务名调用与多实例选择可用 |
| 同步调用失败与重试 | 超时配置生效，失败语义明确，写入不会因无约束重试重复执行 |
| 商品主表与详情路径写入 | 同一数据源本地事务共同成功或回滚；点击读取不创建全局事务 |
| Seata 参与流程 | 定义参与者后验证共同提交、故障回滚、超时恢复及上下文传播 |
| 下单事实与事件 | 本地事务回滚不投递成功事件；提交后崩溃仍可恢复投递；Seata 场景等待全局成功 |
| 消息重复与消费故障 | 业务幂等；消费事务成功后确认；失败有限重试并可追踪补偿 |
| 订单列表或通知延迟 | 不回滚已完成核心下单；恢复后按事件和版本补齐展示或后续处理 |
| Redis 读取与失效 | 命中、回源、过期、更新失效可核验；分页和授权范围不串数据 |
| Redis 故障与并发更新 | 回源有保护，失效失败可恢复，并发旧值回填按约定纠正；Seata AT 的暂态数据缓存在提交、回滚与崩溃恢复场景按约定隔离或修复 |

## 7. 待细化事项

- 各中间件和客户端的具体版本、部署模式、运行资源、账号与环境配置。
- OpenFeign 实际调用清单、服务身份、超时、共享连接池及幂等重试策略。
- Seata 具体跨服务业务、模式、参与数据源、全局事务范围与恢复规则。
- 订单事实模型、下单完成口径、是否存在独立订单列表投影，以及消费者归属。
- RabbitMQ 事件字段、交换机与队列、投递任务、确认、重试与死信、幂等、版本顺序和展示延迟。
- Seata 与成功事件投递的协调方式，避免全局事务完成前发送成功事件。
- Redis 缓存范围、键与版本、TTL、主动失效、并发回源、修复及故障回源保护。

上述细项作为后续设计内容，不表示需要现在创建订单、库存或展示服务，也不表示本次完成了中间件联调。
