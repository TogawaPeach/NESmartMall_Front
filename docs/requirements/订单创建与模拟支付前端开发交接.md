## 2. 前端先行接口契约

下面是本轮为前端准备的目标契约，不是已上线接口；后端新会话需据此实现或先同步修改本文件和前端调用，不能各自采用不同路径。

### 2.1 创建订单

`POST /api/orders`，复用统一 HTTP 客户端和现有 Bearer，不发送 Idempotency-Key 或用户 ID。

```json
{
  "items": [
    { "productId": "23", "quantity": 1 }
  ],
  "recipient": {
    "name": "用户填写的收货姓名",
    "phone": "用户填写的手机号",
    "address": "用户填写的完整地址"
  }
}
```

- items 是本次选中商品与正整数数量，productId 为正整数十进制字符串，去重或拒绝重复条目；不能携带价格、金额、前端状态、订单号或当前用户 ID。
- 收货信息 trim 后必填，长度分别不超过 100、32、500，前端做基础格式与长度校验，服务端仍独立验证。不从登录手机号自动伪造收货手机号，不保存虚构地址。
- 请求体来自点击时冻结的购买意图；请求已发出后，不能因购物车刷新改变这笔订单的数量和商品。
- 后端批量读取商品权威价格，按整数分汇总，确定运费，生成订单及成交快照，条件扣减库存；任一步失败按 Seata 规则整体回滚。只有全局提交成功后才返回创建成功。

### 2.2 确认模拟支付

目标路径为 `POST /api/orders/{orderNo}/pay`，无业务请求体，复用 Bearer。orderNo 来自已经创建或查询到的订单，始终按字符串传递。

- 不重新发送 items、收货信息、金额或创建订单请求，不生成额外 UUID。
- 后端仅允许状态 0 且未到期的订单原子转为状态 1，写入服务端应付金额和付款时间；同单已经支付按幂等语义返回当前已支付结果。
- 本路径独立于现有确认收货 `POST /api/orders/{orderNo}`，不能覆盖或复用确认收货动作。
- 支付超时或断网时，按已知 orderNo 查询订单确认结果，不本地显示成功，不自动重新创建。任何主动再次支付仍按同一 orderNo 操作，由后端状态迁移防重复。

### 2.3 写接口成功响应

创建及支付成功统一采用现有 `Result<Order>` 包装：HTTP 200、业务 code 200、message OK，data 为完整订单详情，并增加支付资格字段。完整对象有利于复用既有详情解析，避免前端使用当前购物车拼造成交快照。

创建成功示例（仅接口格式示例，不是真实订单或默认收货信息）：

```json
{
  "code": 200,
  "message": "OK",
  "data": {
    "orderNo": "JW1980123456789012345",
    "status": "PENDING_PAYMENT",
    "createdAt": "2026-10-19T07:00:00Z",
    "paidAt": null,
    "shippedAt": null,
    "completedAt": null,
    "cancelledAt": null,
    "items": [
      {
        "id": "1001",
        "productId": "23",
        "name": "示例测量杆",
        "model": "示例型号",
        "coverUrl": null,
        "unitPriceFen": 13440,
        "quantity": 1
      }
    ],
    "goodsAmountFen": 13440,
    "shippingFeeFen": 0,
    "discountAmountFen": 0,
    "payableAmountFen": 13440,
    "paidAmountFen": null,
    "recipient": {
      "name": "示例收货人",
      "phone": "138****0000",
      "address": "示例收货地址"
    },
    "logistics": null,
    "payExpireAt": "2026-10-19T07:15:00Z",
    "serverTime": "2026-10-19T07:00:01Z",
    "canPay": true,
    "displayStatus": "PENDING_PAYMENT",
    "cancelReason": null
  }
}
```

- 创建成功时 status 为 PENDING_PAYMENT，但极端延迟返回时 canPay 可能已为 false；此时显示已超时，不允许付款。
- 支付成功时状态通常为 PENDING_SHIPMENT，paidAmountFen 等于订单应付金额，paidAt 非空、canPay=false；若同单已进入后续已支付状态，幂等返回当前事实，不能让状态倒退。
- 价格、名称、型号、数量、款数和总件数全部使用响应的 items；合计使用 payableAmountFen，运费与商品金额可单独展示。当前无优惠，discountAmountFen 为 0；不在前端默认运费始终为 0。
- 所有金额及运算为非负安全整数分；合法 0 元可支付。空明细、非法订单号、金额不一致、缺少新写接口必填字段或畸形成功响应不能变成成功。
- 响应中订单主表 id 与 userId 不对外返回；OrderItem.id/productId 字符串约定不变。支付与按号查询返回的 orderNo 必须与请求一致。

### 2.4 查询及渐进兼容

- 继续使用 `GET /api/orders`（可选 status，data 为数组、不分页）与 `GET /api/orders/{orderNo}`。查询未来增加 payExpireAt、serverTime、canPay、displayStatus、cancelReason，含义见业务需求。
- 旧后端查询暂时没有这些字段时，继续展示原有订单、详情及确认收货；缺少支付资格时禁用继续付款并提示付款信息暂未就绪，不自行生成截止时间或当作可支付。不要因新字段尚未部署让全部旧查询报错。
- 新写接口响应必须完整校验上述字段，不以兼容旧 GET 为由放过畸形创建成功。
- 查询超时订单仍可见，状态 0 已到期显示“支付已超时，订单关闭处理中”，canPay=false；不伪造取消时间，不增加持久化状态或筛选标签。
- 倒计时使用服务端时间与截止时间的差值，并结合本地经过时长展示，到期禁用支付并重新查询；服务端仍拥有最终校验权。

### 2.5 错误与未知结果

- 创建请求已发出后，网络错误、超时、5xx、网关结果未知、成功响应丢失或格式异常，均不能认定未创建。统一显示“下单结果暂未确认，请刷新购物车并查看‘我的订单’”，提供刷新购物车和查看我的订单，不提供直接重试创建。
- 不允许请求库、拦截器、watch、组件重挂载或页面恢复自动重放 POST /api/orders。请求取消不等于后端回滚。
- 只有服务端明确约定为“订单及库存未提交”的校验/业务拒绝响应，才允许修正后重新发起创建。目标接口将 400 用于参数校验，409 用于商品/库存等业务拒绝，且仅在确认未提交时返回；后端无法确认则返回未知结果错误，不伪装业务拒绝。
- 写接口尚未部署的明确 404/405 展示服务暂未开放；不回退原前端假成功。401 沿用会话处理，403 展示权限说明，不能绕过登录继续下单。
- 已知 orderNo 的支付结果未知，提示“支付结果暂未确认，请查看订单”，按号查询恢复，不把“正在关闭”或未查询成功当作已支付。

## 3. 前端状态与交互

建议至少区分：待填写、创建中、创建结果未知、已创建待支付、支付中、支付结果未知、支付成功、已超时/取消；具体命名可按代码风格选择。

- 业务订单状态独立于弹窗开关。创建中阻止重复点击，已创建后点模拟支付只打开原单确认，不重新下单；暂不支付、Esc、关闭小票不取消订单。
- 创建结果未知后，关闭/重开小票不能清除未知标记变成直接重新创建；提供明确的订单查询恢复入口。同一会话可在账户范围保存必要的已知 orderNo/未知状态，不生成下单 UUID，也不实现“刷新后自动重试”。
- 新购买必须是用户明确发起的新意图，不能由超时回调或普通 reset 自动触发。完整跨刷新与跨标签防重不在本期保证内。
- 账号退出、过期或跨标签切换时清理旧账户 UI，不使用旧 orderNo 发新账户请求；迟到结果不覆盖新会话。后端可能已提交这一事实不变。
- 前端不主动 DELETE 购物车条目，也不靠 local items.splice 模拟后端清理。只通过现有 GET 刷新购物车；异步清理延迟时允许条目暂留，提示先查看订单。
- 已创建订单快照独立保存，不能再绑定会被刷新或后端清理的 selectedItems。现有 CartView 的 watch 会关闭小票、useCheckoutPayment.reset 会清空状态，接入时需调整，避免购物车更新擦掉已创建订单、支付结果或未知结果提示。
- 下单成功后附带的购物车 GET 刷新失败，不得把已经成功的创建改判失败，更不能补发创建。小票商品数量和款数均以订单快照计算。
- 保留金额格式化、焦点与键盘操作、移动端滚动、减少动态效果适配。新增表单需有可访问标签及清晰校验；本次不重做整体视觉。
- 替换“不会生成订单”为“将创建订单，模拟支付不会实际扣款”；移除“确认后直接显示成功”等旧承诺，价格查询中状态改为创建订单中。

## 7. 2026-10-19 前端实际交付及最终契约补充

前端路径：`/Users/lightfull/NESmartChoice_Before/NESmartMall`。第 2 节路径和请求/响应结构已落地；它们是后端后续必须实现的目标接口，尚不能视为真实接口已上线。

### 7.1 路径及严格边界

| 动作 | 路径 | body | 成功判定 |
| --- | --- | --- | --- |
| 创建订单 | POST /api/orders | 仅 items[{productId:string,quantity:正安全整数}] 和 recipient{name,phone,address} | HTTP 200、code 200、message 精确为 OK、完整合法 Order，status=PENDING_PAYMENT |
| 模拟支付 | POST /api/orders/{orderNo}/pay | 无业务 body | 同上完整 Order；orderNo 必须等于请求；状态为 PENDING_SHIPMENT / PENDING_RECEIPT / COMPLETED，paidAt 非空，paidAmountFen 等于 payableAmountFen（含 0） |
| 原单恢复 | GET /api/orders/{orderNo} | 无 | 沿用详情解析，订单号一致；明确已支付事实才能恢复支付成功 |
| 确认收货（保留） | POST /api/orders/{orderNo} | 无业务 body | 沿用现有 code 200 判定；与 /pay 完全独立 |
| 列表 | GET /api/orders?status=... | 无 | data 数组，不分页，不过滤超时订单 |

- 创建请求白名单组装，不带用户 ID、金额、UUID、Idempotency-Key 或预申请订单号。重复 productId 被拒绝，收货信息 trim 后发送。姓名必填最多 100 字、地址必填最多 500 字；手机号基础格式为 7–32 字符，可有开头 +、数字、空格、括号和连字符，数字至少 7 位；服务端需独立业务验证。响应可返回脱敏手机号。
- 新写响应必需保留第 2.3 节所有详情字段，包括可空时间、物流和支付资格字段；不能返回摘要或空对象。金额是非负安全整数分，明细非空，明细 ID 不重复，明细金额之和等于 goodsAmountFen，商品+运费−优惠等于应付；本期 discountAmountFen 必须为 0。服务端计价、运费和成交快照优先于当前购物车参考价。
- 时间必须为带 Z 或明确时区的 ISO 字符串。payExpireAt 与 createdAt 固定相差 900000 毫秒；serverTime 是本次响应时间，不能缓存成创建时间。待付款且 serverTime < payExpireAt 时 canPay=true/displayStatus=PENDING_PAYMENT；到期时 canPay=false/displayStatus=PAYMENT_EXPIRED；其他状态 canPay=false/displayStatus=status。未取消时 cancelReason=null，超时取消用 PAYMENT_TIMEOUT。
- 旧 GET 若五个新增字段全部缺失，继续展示与确认收货；不给旧单推算截止时间、不授予支付资格。部分支付字段存在时按完整组校验，不能用残缺资格开放付款。后端部署 GET 新字段时需整组返回。
- HTTP 400/409（或 HTTP 200 内同值业务 code）仅代表服务端保证订单与库存未提交的明确拒绝，允许修改后下单；HTTP/业务 404/405 展示交易服务暂未开放，401 走统一会话清理，403 展示权限说明。任何不能保证未提交的情况必须返回未知结果，而非冒充 400/409。
- 其他创建失败、畸形/不完整成功、非预期成功状态都锁定为未知结果，显示“下单结果暂未确认，请刷新购物车并查看‘我的订单’。”，无自动重试和直接重下单按钮。

### 7.2 前端状态及账号隔离

- `src/stores/checkout.ts` 在当前 Pinia/页面会话中保存 draft / creating / unknown / created 和完整订单，独立于弹窗、selectedItems 与购物车 GET；关闭、Esc、路由卸载均不清除交易事实。全页面刷新及跨标签严格防重不在保证范围，不持久化收货信息或下单键。
- 暂不支付仅关闭确认框；重新打开原单前查询最新详情；支付未知时自动 GET 原 orderNo，查询失败保留未知并禁用再次支付，提供手动查询及订单入口。已知订单有明确“开始新的购买”，不会由回调或普通 reset 自动创建新意图；创建未知不提供该重置入口。
- 创建成功后仅附带 GET 刷新购物车，失败或商品暂留不改变订单结果；从不在结算流程 DELETE 或本地删行。购物车原有用户主动删除功能保持原样。
- 登出、过期或 token 切换会清空旧收货/订单 UI，并忽略旧响应。订单请求新增纯客户端 expectedAuthorization 元数据，统一 HTTP 拦截器在实际发送前核对发起会话，失配则阻止请求；此字段不会进入请求 body、URL 或 HTTP header，也不是后端接口字段。
- 倒计时锚定服务端时间差和 performance.now 的本地经过时长，按钮点击时再次计算，避免后台定时器节流后付款。到期只自动查询一次，不轮询创建/支付，不伪造取消时间或状态。

### 7.3 显式开发模拟与真实联调边界

```sh
VITE_CART_MOCK=true VITE_CART_MOCK_SCENARIO=normal VITE_ORDER_MOCK=true npm run dev
```

两项模拟都开启才接受交易写模拟；单开订单模拟仅保留查询验收，写入返回 404，避免拿真实购物车制造模拟付款成功。仅 Vite 非 production 的 serve 安装模拟；生产构建及真实 API 失败不回退样本。已有 normal / empty / forbidden / unavailable / error / malformed 保留，新增 create-unknown、create-malformed、pay-unknown、expired。创建样本按隔离目录重新计价、生成本地模拟 JW 号与 15 分钟期限；支付修改同一模拟订单，GET 可恢复，0 元可支付，超时仍待付款可查且不伪装关单完成。模拟订单按 Bearer 会话隔离，购物车故意暂留以验收清理延迟；不模拟 Seata、真实扣库存、可靠消息、取消回补或真实购物车清理成功。

浏览器使用临时 /tmp QA 服务提供明确标注的虚构登录会话，未加入生产或项目认证代码；全部收货数据为虚构验收数据。测试与截图位于前端 `docs/verification/订单创建与模拟支付验证记录.md` 及 `docs/verification/checkout/`。

后端接手先实现第 7.1 节 DTO/Controller/Result<Order>，特别是 message=OK、完整快照与支付字段；再逐步实现权威计价/运费、Hutool 订单号、库存条件扣减、短事务 Seata、按原单支付、15 分钟互斥关单回补、全局提交后 RabbitMQ 可靠投递与购物车版本保护清理。HTTP 400/409 的未提交保证、未知错误恢复、跨用户鉴权、并发支付/取消、重复消息幂等必须真实联调；开发模拟无法证明这些服务端性质。
